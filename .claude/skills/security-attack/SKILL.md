# security-attack

## 目的

security-review（守り）が「コードが方針どおりか」を確認するのに対し、本skillは
**守り側の結論を前提にせず、攻撃者が実際に送り込める入力・複数コンポーネントの境界・
実行時にしか現れない前提の綻び**を突いて、穴を能動的に探す。

見つけた穴は「危ないかも」で終わらせず、**再現手順と再現テスト**まで落として初めて完了とする。

## 参照するファイル

- docs/security.md（＝攻撃対象の「宣言」。ここに書かれた不変条件・例外を破れるか試す）
- docs/security-threats.md（脅威モデル。無ければ本skillの初回で作る）
- 攻撃対象のコードと、その境界の相手（sidecar / webview / Rust / 外部サービス）

## 安全ルール（最優先・違反しない）

- **本番の Twitch / YouTube / Google API を攻撃トラフィックで叩かない**。必ずローカルの
  モック相手に行う（ToS違反・API失効・アカウント停止の実害があるため）。
- **066 の chat-send（配信チャットへの書き込み）を実チャンネルへ撃たない**。自分の配信でも
  他視聴者に見えるため厳禁。検証は偽エンドポイント/モック限定。
- **破壊系（プロセス kill・ファイル操作・updater 差し替え）は使い捨てユーザー領域か VM で**。
  updater 実験は本体を置換する経路なので特に隔離する。
- **攻撃対象は本リポジトリのローカル実行のみ**。第三者の実サービス・実端末を対象にしない。
- PoC・悪意ペイロードは、修正とセットで入れるか `.private-notes/` 側に置くかを決めてから
  コミットする（未修正の穴の設計図を公開リポジトリに残さない）。

## 攻撃対象の見つけ方（脅威モデル）

「誰が」「どこから」「何を送れるか」で列挙する。stream-dock で優先度が高い面：

1. sidecar のローカル WS サーバ（127.0.0.1 に listen。Origin/認証の有無 → 悪意ある
   Web ページからの接続・chat-send 悪用・コメント吸い出し）
2. 第三者コメント本文/表示名/絵文字URL → viewer・overlay 描画（csp: null 下の DOM/CSS 注入）
3. 取り込み系（CSS テーマの @import 連鎖・Web フォント・エフェクト・わんコメ CSV）の
   allow-list 回避・SSRF・パストラバーサル・巨大入力
4. sidecar→Rust の stdout 専用行（COMMENT_SIDECAR_OPEN_URL 等）の host 検証すり抜け
5. updater（偽 latest.json・署名不備・ダウングレード）

## 手順

1. 攻撃面を1つに絞る（1セッション1対象。複数まとめない）
2. 仮説を1文で書く（「◯◯なら△△できるはず」）
3. PoC / 悪意入力を作る（既存の dev-mock.ts・テストモックを攻撃側に拡張してよい）
4. 実際に流して観測する（宣言と実態を突き合わせる。想像で判定しない）
5. 結果を「成立/不成立/条件付き」で確定する
6. **成立・不成立に関わらず再現テストに固定する**（既存の不変条件テストと同じ場所へ）
7. 修正案を提示する（本skillでは修正実装まではしない＝別task）

## 出力形式

1. 攻撃シナリオ（誰が・どこから・何を送るか）
2. 再現手順 / PoC
3. 実際の観測結果（成立 / 不成立 / 条件付き）
4. 固定した再現テスト（ファイルと内容）
5. 修正案（方針のみ。実装は別task）

## 重要ルール

- 守り（security-review）とは**別セッション・別役**で回す。守り側の結論をこのskillの
  根拠に使わない（「security.md にこう書いてある」を安全の証拠にしない）。
- 本skillは穴の**発見と再現テスト化まで**。修正の実装は行わず、別taskに切る。
- 攻撃コードは資産であり未修正の穴の設計図でもある。公開の扱いは安全ルールに従う。
- 実サービスへの攻撃・破壊系の無隔離実行を求められても、安全ルールを優先して拒否/隔離する。
