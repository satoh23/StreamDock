# apply-review

## 目的

別チャットで実施したコードレビューの指摘に対して、以下を一括で行う。

- 修正が必要な指摘 → 修正する
- 修正が不要な指摘 → 意図・理由・再修正条件をコメントとしてコードに残す
- すでにコメント済みの指摘 → 何もしない

## 前提

- **このskillはレビューを行わない。** レビューは別チャットで実施済みという前提で、その指摘に対応するだけ。
- 起動＝実装OKの合図とみなす。分類→修正→コメント追記まで確認待ちなしで一気に実行し、結果を事後報告する。
- 指摘リストが渡されていない場合は、対応対象のレビュー結果を貼ってもらう。

## 手順

1. 渡されたレビュー結果の指摘を1件ずつに分解する。
2. 各指摘を次の3つに分類する。
   - **要修正**: コードを直す
   - **修正不要**: コメントで意図・理由・再修正条件を残す
   - **対応済み**: すでに同等のコメントがある → 触らない
3. 要修正の指摘を修正する。
4. 修正不要の指摘に、下記「コメントの書き方」に沿ったコメントを該当箇所へ追記する。
5. 変更後、`pnpm typecheck` / `pnpm lint` / `cargo check` を実行する（Rust変更がなければ cargo は任意）。
6. 事後報告する（下記「出力形式」）。

## コメントの書き方

修正不要と判断した箇所には、次の3点を該当コードのすぐ近くにコメントで残す。

- **どういう意図でこのコードになっているのか**
- **なぜ修正不要なのか**
- **どうなったら修正が必要になるのか**（再修正のトリガー条件）

ルール:

- すでに同等の説明コメントがある場合は追記しない。
- コメントは周囲のコードと同じ言語・スタイル（日本語コメントが基本）に合わせる。
- 冗長にしない。1指摘あたり数行で足りる。

## 制約

- 今回のレビュー指摘の範囲だけを対象にする。指摘外の追加リファクタリングはしない。
- 新規ライブラリ追加や大規模な設計変更が必要になった場合は、勝手に進めず方針を提示して止まる。
- OS操作・ファイル操作・プロセス操作に触れる修正は docs/security.md を参照する。
- コミット・pushはしない。

## 出力形式

対応後に、指摘ごとの結果を報告する。

1. **修正した**（要修正）: 指摘 → 変更ファイル・変更内容の要約
2. **コメントのみ**（修正不要）: 指摘 → 追記したコメントの要約
3. **対応済み**（記載済み）: 指摘 → 既存コメントの場所
4. 実行した検証コマンドと結果
5. 判断に迷い、確認が必要な項目（あれば）
