## 目的

**取り込んだテーマの書体を反映する。**

## ⚠⚠ なぜ 060c だけでは足りないのか（2026-08-05 の実測）

依頼者の実サンプルが `@import` する外部 CSS は、**Google Fonts を 6 本** `@import` していた
（`Zen Kaku Gothic Antique` / `M PLUS 1p` / `Hachi Maru Pop` ほか）。

060c がその CSS を取得してインライン化しても、中身は

```css
@font-face{font-family:'Zen Kaku Gothic Antique';src:url(https://fonts.gstatic.com/…woff2) format('woff2')}
```

であり、**この `src` の外部 URL は 060b のサニタイザが宣言ごと除去する**（許可形は `data:` のみ）。
＝ **`@font-face` は残るが `src` が消え、書体は反映されない。**

⚠ したがって **「060c を実装すれば思ったとおりになる」は、意匠については成立するが書体については成立しない。**
本タスクはその最後の 1 段を埋める。

## やること（骨子）

1. インライン化した CSS の中から **`@font-face` の `src` にある `http(s)` の URL だけ**を取り出す。
2. 060c と**同じ SSRF ガード・同じ同意経路**でそれを取得する。
3. `woff2` / `woff` を **base64 の `data:` URI** へ変換し、`src` を書き換えて保存する。

## ⚠⚠ 未解決の設計問題（着手前に結論を出すこと）

### 問題① 取得が 2 段になる（宛先ホストが増える）

`fonts.googleapis.com`（CSS）→ `fonts.gstatic.com`（フォント実体）の **2 ホスト**を踏む。
060c の同意ダイアログは「ユーザーの CSS に書かれた 1 つの宛先」を見せる設計なので、
**「その先でさらに別ホストへ接続する」ことをどう見せるか**を決める必要がある。

- ⚠ 060c の申し送り⑥「**同意ダイアログはホストを別途強調して出すこと**」（userinfo 付き URL の表示偽装対策）は
  そのまま効く。2 段目のホストも**同じ強調で列挙**すること。
- ⚠ 「1 段目に同意したら 2 段目も自動」にするか「2 段目も個別同意」にするかは**未決**。
  前者なら「同意した宛先」と「実際に接続した宛先」が食い違う。

### 問題② 再帰の深さと対象を厳密に限る

⚠⚠ **辿ってよいのは「`@font-face` の `src` の url」だけ・深さ 1 段だけ**にすること。

- `background-image: url(https://…)` まで辿ると、**任意の外部画像取得＝トラッキングピクセル**になる。
  ⚠ 「CSS の中の url を取得する」という一般化を**絶対にしない**（§1 の例外を無制限に広げる形）。
- 取得したフォント CSS の中にさらに `@import` があっても**辿らない**（深さ 1 段で打ち切る）。

### 問題③ ⚠⚠ 256KB 上限と正面衝突する

日本語 Web フォントは Google Fonts が **unicode-range で約 110 分割**して配信しており、
**合計 1〜4MB**、base64 化で **さらに +33%**。現行の `MAX_CSS_BYTES = 256KB` では**まったく入らない**。

決めるべきこと:

- 上限をいくつにするか（フォント込みの総量）。⚠ **256KB は 060a の実測に紐づく「注入経路の予算」**
  （`rewriteSelectors` は 060d が注入のたびに毎回走らせる）であって、単なる安全弁ではない。
- **unicode-range の分割をどう扱うか**（全部入れる／日本語常用の分割だけ／`display=swap` のサブセットだけ）。
  ⚠ 「使う文字だけサブセット化」は**不可能**（コメント本文は実行時に決まる）。

### 問題④ ⚠⚠ フォントは CSS 本体と**別ファイル**に保存する必要がある

フォントの data URI を CSS 本文と同じ文字列に混ぜると、
**テーマを切り替えるたびに `rewriteSelectors` が数 MB を走査する**。

→ **`themes/<uuid>.css`（意匠）と、フォント用のもう 1 ファイルに分け、注入も別の `<style>` にする**こと。
フォント CSS は `@font-face` だけでセレクタを持たないので、**変換も走査も要らない**。

⚠⚠ **これは既存の契約を 2 つ壊す（設計どおり壊れる）**:

| 契約 | どう壊れるか |
|---|---|
| `is_managed_file_name()` が `<uuid v4>.css` の**完全一致**を要求 | 2 つ目のファイル名を許す形へ広げる必要がある |
| `exactly_one_place_sanitizes_and_exactly_one_place_writes`（`std::fs::write(` が service.rs に 1 回） | 書き込みが 2 か所になる／または 1 か所のまま 2 ファイル書くヘルパへ寄せる |

⚠ **数字だけ書き換えて通さないこと。** `docs/security.md` **§5 の例外節**（「保存先の組み立てにユーザー入力を
1 バイトも結合しない」「書けるのは `store_sanitized_css` だけ」）の**書き直しが要る**＝
**security-review の対象**である。落ちること自体がレビューを呼ぶための仕掛けとして置かれている。

### 補足（ライセンス）

取得したフォントは**ユーザー端末の `app_data_dir` に置くだけ**で再配布ではないが、
**ユーザーが任意の URL を指定できる以上、ライセンスは確認できない**。
→ **「取り込むフォントの利用条件はユーザー自身の責任」を UI と docs に明記すること。**

## やらないこと

- **StreamDock 本体へのフォント同梱**（アプリサイズとライセンス確認が別問題になる）。
- `@font-face` 以外の url の取得（問題②）。
- サブセット化・フォント変換（woff2 をそのまま埋め込むだけ）。

## 代替案（本タスクを実装しない場合に必ず入れるもの）

⚠ 本タスクが重い場合の**最低限の代替**として、[060c](060c-external-css-snapshot.md) 側で次を出すこと:

> 「このテーマは **○○** というフォントを指定していますが、StreamDock は外部からフォントを読み込みません。
> 端末にインストールすると反映されます。」

フォント名は**除去した `@font-face` / `@import` の宛先**から拾える。⚠ **§1 を一切曲げずに、
ユーザーに次の行動を示せる**ので、本タスクの完成を待たずに価値が出る。

## 実装後に必要なレビュー

⚠⚠ **security-review 必須**。理由:

- **§1 の例外を 2 段目（別ホスト）へ広げる**。
- **§5 の「書けるのは 1 か所・`<uuid>.css` だけ」を広げる**（契約テストが落ちる）。
- 新しい取得対象（バイナリ）を扱う＝ **Content-Type / サイズ / タイムアウトの上限**が新規の検証点になる。
