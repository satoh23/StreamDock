## 目的

**取り込んだテーマの書体を反映する。**

> ⚠⚠ **060f 追修正③（2026-08-08）で、依頼者の実サンプルに残る差分は「書体」だけになった。**
> 縦バー（クラス形セレクタ）と文字色（`:root` の `--txtcolor`）は出るようになったので、
> **本タスクが実サンプル忠実化の最後の 1 ピース**である。詳細は `docs/progress.md` の 060f 節「差し戻し③」。

## ⚠⚠ なぜ 060c だけでは足りないのか（2026-08-05 の実測）

依頼者の実サンプルが `@import` する外部 CSS は、**Google Fonts を 6 本** `@import` していた
（`Zen Kaku Gothic Antique` / `M PLUS 1p` / `Hachi Maru Pop` ほか）。

060c がその CSS を取得してインライン化しても、中身は

```css
@font-face{font-family:'Zen Kaku Gothic Antique';src:url(https://fonts.gstatic.com/…woff2) format('woff2')}
```

であり、**この `src` の外部 URL は 060b のサニタイザが宣言ごと除去する**（許可形は `data:` のみ）。
＝ **`@font-face` は残るが `src` が消え、書体は反映されない。**

⚠ したがって **「060c を実装すれば思ったとおりになる」は、意匠については成立するが書体については成立しない。**
本タスクはその最後の 1 段を埋める。

## やること（骨子）

1. インライン化した CSS の中から **`@font-face` の `src` にある `http(s)` の URL だけ**を取り出す。
2. 060c と**同じ SSRF ガード・同じ同意経路**でそれを取得する。
3. `woff2` / `woff` を **base64 の `data:` URI** へ変換し、`src` を書き換えて保存する。

## ⚠⚠ 未解決だった設計問題（→ 結論済み）

### 問題① 取得が 2 段になる（宛先ホストが増える）

> ✅ **結論: 「1 段目に同意したら 2 段目も自動」は採らない。段ごとに必ず同意を取る。**
> - **1 段目・2 段目**は 060c のまま**1 件ずつ**（完全な URL ＋ ホストを別行で強調・既定はキャンセル）。
>   2 段目は文言を変えて「**1 段目で取得した内容が参照している別のアドレス**」であることを示す。
> - ⚠ **1 段目のダイアログに 1 行足した**——「取得した内容がさらに別のアドレスを参照していた場合は、
>   **改めて確認します**（自動では取得しません）」。1 段目の時点では 2 段目の宛先を**知りようがない**
>   （まだ取得していない）ので、これが誠実な書き方である。
> - **3 段目（フォント）だけはホスト単位で 1 枚**にまとめた。日本語 1 ファミリで約 110 本になり、
>   110 枚のダイアログは同意として機能しない（読まずに押されて担保が空洞化する）。
>   ⚠ **完全な URL を全部は出さない**ので、代替の担保を置いた:
>   ①ダイアログのホスト集合は**実際に取得する URL 群から導出した集合そのもの**
>   ②取得ループはその URL 群以外を 1 本も送らない（テストで固定）
>   ③sidecar 側が 1 本ごとに `assertAllowedThemeFontUrl` を再度通す
>   ④**同意の前に**「候補 N 件のうち M 件」「上限（約 4MB）」を出す。

`fonts.googleapis.com`（CSS）→ `fonts.gstatic.com`（フォント実体）の **2 ホスト**を踏む。
060c の同意ダイアログは「ユーザーの CSS に書かれた 1 つの宛先」を見せる設計なので、
**「その先でさらに別ホストへ接続する」ことをどう見せるか**を決める必要がある。

- ⚠ 060c の申し送り⑥「**同意ダイアログはホストを別途強調して出すこと**」（userinfo 付き URL の表示偽装対策）は
  そのまま効く。2 段目のホストも**同じ強調で列挙**すること。
- ⚠ 「1 段目に同意したら 2 段目も自動」にするか「2 段目も個別同意」にするかは**未決**。
  前者なら「同意した宛先」と「実際に接続した宛先」が食い違う。

### 問題② 再帰の深さと対象を厳密に限る

> ✅ **結論: 規則を 1 本に書き下した（`docs/security.md` §1 の 060h 追補が正）。**
> ① **CSS** … `@import` の宛先。**深さ 2 まで**（1 段目＝ユーザー CSS／2 段目＝1 段目で取得した CSS の中）。
>   **3 段目以降は追わない。** ⚠ 深さ 1（060c）では Google Fonts の CSS に到達できず、書体が 1 バイトも
>   入らない（実サンプルの実構造・下記⑥）。深さは **`MAX_IMPORT_ROUNDS = 2` の定数 1 つ**が決める。
> ② **フォント** … **`@font-face` ブロック内の `src` 宣言**にある url だけ。そこから先は一切辿らない。
> **それ以外の url は 1 つも取得しない**（`background-image` / `cursor` / `list-style-image` / `mask` /
> `filter` / `@namespace` / `@import` 内の `data:`）。
> **構造的な担保**: 候補 URL を作れるのは **Rust のサニタイザ 1 か所だけ**で、
> `stripped_font_faces` に載る条件は「`@font-face` の直下」かつ「プロパティ名が `src`」の AND
> （走査器がブロックの入れ子を辿った結果として決まる＝正規表現ではない）。
> ⚠ **ミューテーションで実効性を確認済み**（`in_font_face` を外す／`property=="src"` を外す＝どちらも RED）。

⚠⚠ **辿ってよいのは「`@font-face` の `src` の url」だけ・深さ 1 段だけ**にすること。

- `background-image: url(https://…)` まで辿ると、**任意の外部画像取得＝トラッキングピクセル**になる。
  ⚠ 「CSS の中の url を取得する」という一般化を**絶対にしない**（§1 の例外を無制限に広げる形）。
- 取得したフォント CSS の中にさらに `@import` があっても**辿らない**（深さ 1 段で打ち切る）。

### 問題③ ⚠⚠ 256KB 上限と正面衝突する

> ✅ **結論: 意匠の 256KB は動かさない。フォントを別ファイル・別上限にする。**
>
> | 定数 | 値 | 根拠 |
> |---|---|---|
> | 意匠 CSS（**据え置き**） | 256KiB | 060a の実測に紐づく**注入経路の予算**。`rewriteSelectors` は注入のたびに毎回走る |
> | フォント 1 本（生 woff2） | **512KiB** | Google の日本語サブセットは 1 本 4〜40KB。**分割していない CJK フォント丸ごと（1〜4MB）は落ちる**＝ 1 本で予算を食い潰す形を構造的に排除 |
> | フォント総量（生 woff2 合計） | **3MiB** | base64 で 4MiB。**日本語 1 ファミリ（約 110 分割）が丸ごと入る**値 |
> | 保存するフォント CSS | **5MiB**（`MAX_FONT_CSS_BYTES`） | 4MiB の data URI ＋ `@font-face` の記述（1 ブロック約 200B × 256 ≒ 50KB）＋ 余裕 |
> | `@font-face` の本数 | **256 本** | 日本語 1 ファミリ 110 分割の 2 倍強（Rust の `MAX_STRIPPED_FONT_URLS` と同値） |
>
> **なぜフォント側は 5MiB でよいのか**＝フォント CSS は `rewriteSelectors` も `scopeSelectors` も
> `withDecorationReset` も**通らない**（`@font-face` はセレクタを持たない）ので、注入時のコストは
> 「ブラウザが CSS を 1 回パースする」だけ。256KB の根拠（毎回走る O(n) の変換）が及ばない。
>
> **unicode-range の分割の扱い＝ C 案（3 段の規則）**:
> ① **テーマが実際に使っているファミリだけ**（実サンプルは 6 ファミリを `@import` するが、
>   `font-family` で指しているのは 1〜2 ファミリ。絞らないと約 660 ブロック・10MB 超で予算に入らない）
> ② **`unicode-range` を持たないものを優先**（全字面を覆うので部分取得でも見た目が安定する）
> ③ **宣言順に、本数の予算まで**
> ⚠ 使用集合が取れない（`var()` 経由など）／ファミリ名が読めないときは**絞り込まない**（落とさない側へ倒す）。
> ⚠ **「使う文字だけサブセット化」は不可能**（コメント本文は実行時に決まる）——これは変わらない。
> 予算に収まらなかった文字は**端末のフォントで表示される**ので、その旨を取り込み結果に出す。
> ⚠ **ディスクの天井が上がる**（256KB×200 ≒ 50MB → (256KB+5MiB)×200 ≒ 1GB）。
> **200 件上限は据え置き**（`docs/security.md` §5 の 060b 例外節④に再修正トリガーを記載）。

日本語 Web フォントは Google Fonts が **unicode-range で約 110 分割**して配信しており、
**合計 1〜4MB**、base64 化で **さらに +33%**。現行の `MAX_CSS_BYTES = 256KB` では**まったく入らない**。

決めるべきこと:

- 上限をいくつにするか（フォント込みの総量）。⚠ **256KB は 060a の実測に紐づく「注入経路の予算」**
  （`rewriteSelectors` は 060d が注入のたびに毎回走らせる）であって、単なる安全弁ではない。
- **unicode-range の分割をどう扱うか**（全部入れる／日本語常用の分割だけ／`display=swap` のサブセットだけ）。
  ⚠ 「使う文字だけサブセット化」は**不可能**（コメント本文は実行時に決まる）。

### 問題④ ⚠⚠ フォントは CSS 本体と**別ファイル**に保存する必要がある

> ✅ **結論: 別ファイル・別 `<style>` にした。⚠⚠ ただし「壊れる」と予告されていた契約テスト 2 つは、
> 設計を変えて**壊さずに済ませた**（下の表は**実コードを読んだ結果とは違っていた**）。**
>
> | 契約 | 本ファイルの予告 | **実際** |
> |---|---|---|
> | `is_managed_file_name()` の `<uuid v4>.css` 完全一致 | 壊れる | **壊していない**。フォント資産にも**別の uuid v4 を採番**するのでファイル名は `<uuid v4>.css` のまま＝**書けるファイル名の集合は 1 バイトも広がっていない**。持ち先は DB の新カラム `font_file_name` |
> | `exactly_one_place_sanitizes_and_exactly_one_place_writes` | 壊れる | **壊していない**。2 本目の保存経路（`attach_theme_fonts`）は私有ヘルパ `write_sanitized_asset` へ委譲するだけで、`sanitize::sanitize_css(` と `std::fs::write(` はソース上 1 か所のまま。⚠ **数字合わせではなく、テストが守っている不変条件（保存経路が 2 本に分かれない）を実際に維持している** |
>
> **代わりに設計どおり落ちたのは別の 2 つ**で、どちらも「落ちること自体がレビューを呼ぶ仕掛け」:
> - `exposes_exactly_seven_single_purpose_commands`（**7 → 9**。`attach_overlay_theme_fonts` /
>   `get_overlay_theme_font_css`）
> - `takes_no_arbitrary_path_or_content_from_the_frontend`（`css: String` の出現回数 **2 → 3**）
>
> **`docs/security.md` §5 の 060b 例外節へ「④ フォント資産の再評価」を書いてから**数字を上げた
> （増えないもの／増えるものを分けて記録）。
> ⚠ **静的ガード (10-i) は「4 本目が増えて落ちる」と予告されていたが、実際は落ちない**——
> あれは**ファイル単位の allow-list** なので、既に許可されたファイル（`OverlayApp.tsx` /
> `OverlayThemeCard.tsx`）の中に 2 本目の `<style>` を足しても検出できなかった。
> → **「ファイル → 本数」の Map へ強化した**（060d review S-5 と同型の穴が残っていた）。

フォントの data URI を CSS 本文と同じ文字列に混ぜると、
**テーマを切り替えるたびに `rewriteSelectors` が数 MB を走査する**。

→ **`themes/<uuid>.css`（意匠）と、フォント用のもう 1 ファイルに分け、注入も別の `<style>` にする**こと。
フォント CSS は `@font-face` だけでセレクタを持たないので、**変換も走査も要らない**。

⚠⚠ **これは既存の契約を 2 つ壊す（設計どおり壊れる）**:

| 契約 | どう壊れるか |
|---|---|
| `is_managed_file_name()` が `<uuid v4>.css` の**完全一致**を要求 | 2 つ目のファイル名を許す形へ広げる必要がある |
| `exactly_one_place_sanitizes_and_exactly_one_place_writes`（`std::fs::write(` が service.rs に 1 回） | 書き込みが 2 か所になる／または 1 か所のまま 2 ファイル書くヘルパへ寄せる |

⚠ **数字だけ書き換えて通さないこと。** `docs/security.md` **§5 の例外節**（「保存先の組み立てにユーザー入力を
1 バイトも結合しない」「書けるのは `store_sanitized_css` だけ」）の**書き直しが要る**＝
**security-review の対象**である。落ちること自体がレビューを呼ぶための仕掛けとして置かれている。

### 補足（ライセンス）

取得したフォントは**ユーザー端末の `app_data_dir` に置くだけ**で再配布ではないが、
**ユーザーが任意の URL を指定できる以上、ライセンスは確認できない**。
→ **「取り込むフォントの利用条件はユーザー自身の責任」を UI と docs に明記すること。**

## やらないこと

- **StreamDock 本体へのフォント同梱**（アプリサイズとライセンス確認が別問題になる）。
- `@font-face` 以外の url の取得（問題②）。
- サブセット化・フォント変換（woff2 をそのまま埋め込むだけ）。

## ⚠⚠ 実装して判明した前提（着手前の記述との差分・2026-08-09）

着手前の想定と**実コードが食い違っていた点が 3 件**あった。どれも「読まないと分からない」種類のもの。

1. ⚠⚠ **`@font-face` の `src` の URL は、平坦な配列では返せない。**
   保存される CSS からは **`src` 宣言が丸ごと消える**（`font_face_src_is_removed_but_the_block_survives`）ので、
   「どの URL がどの `@font-face` のものか」を**保存後の CSS から復元できない**（URL がどこにも残っていない）。
   取り込む書体を選ぶには `font-family`（テーマが実際に使っているか）と `unicode-range`（分割のどの範囲か）が
   要るため、**`stripped_font_faces: Vec<StrippedFontFace>`（ブロック単位）で返す**形にした。
   ⚠ これは「frontend が CSS を解析しない」を守るための形でもある——解析を frontend へ置くと
   `background-image` まで拾える実装が生まれ、それはトラッキングピクセルの取得経路である。
   ⚠ 最初は `Vec<String>` で実装し、**テストが落ちて初めて**この事実に気づいた（設計の穴だった）。
2. ⚠⚠ **クエリの解禁だけでは Google Fonts に到達できない。**
   `https://fonts.googleapis.com/css2?family=…` の `pathname` は **`/css2`** で、**`.css` で終わらない**
   （v1 は `/css`）。060c の申し送りは「クエリ禁止の緩和」しか予告していなかったが、
   **パスの形も緩める必要があった**（`.css` 終端 **または** 最後のパス片が `css` ＋ 数字 0 個以上）。
   ⚠ ホストは 1 つも allow-list へ足していない（あくまで「形」の規則）。
3. ⚠ **静的ガード (10-i) は本タスクを検出できなかった**（問題④の結論を参照）。
   ファイル単位の allow-list だったので、既存ファイルに 2 本目の `<style>` を足しても緑のままだった。
