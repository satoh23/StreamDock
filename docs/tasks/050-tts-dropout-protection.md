## 目的

「読まれるコメントと読まれないコメントがある」の根本は、**読み上げが黙って諦める経路が 3 つある**こと。
どれも `console.debug` か無言で、**ユーザーには壊れているようにしか見えない**。捨てるなら見せる／詰まるなら塞ぐ。

### 経路1: backlog 上限による「古い未読の破棄」（無言）

- **`MAX_BACKLOG` を 20 → 6 に下げた**（下記「実機で分かったこと」）。
- **課金イベントは専用の優先キュー**（`priorityQueue`）へ載せ、**破棄せず・通常キューより先に読む**ようにした

[`ttsQueue.ts`](../../apps/desktop/src/features/comment-viewer/ttsQueue.ts) 279-293 行:

```ts
if (isPriority?.(comment)) {                 // 課金＝捨てない・先に読む（49 行の MAX_PRIORITY_BACKLOG=50 は防御用）
  priorityQueue.push(text);
  ...
} else {

```

**残る課題は「捨てたことが見えない」こと**（本タスクの (1)）＝ 上の変更は「何を捨てるか」を直しただけで、
`console.debug` 止まりなのは変わっていない。

#### 実機で分かったこと（2026-07-31・本タスクの前提を書き換える実測）

**読み上げは到着に構造的に追いつかない**。048 の既定 60 文字は VOICEVOX で 10〜13 秒かかるが、
dev-mock は 1800ms 間隔／provider なので:

| 接続 | 到着間隔 | 1 件読む間に届く数 |
| --- | --- | --- |
| provider 1 本 | 1.8 秒 | **5.6〜7.4 件** |
| provider 2 本 | 0.9 秒 | **11.1〜14.8 件** |

＝ **キューは定常的に満杯**になり、経路1 が**常時**発動している（048 の「60 文字なら破棄 0 件」は
「1 件の長文の直後に何件届くか」の試算で、**定常状態の到着レートを見ていなかった**）。
さらに `MAX_BACKLOG=20` は**満杯の消化に 3〜4 分**かかるため、読み上げが画面から数分遅れて
「今は流れていないコメントを延々読む」状態になっていた（＝「同じコメントが何度も読まれる」の正体）。
6 件なら遅延の上限が **1 分程度**に収まる。

⚠ **`(4) MAX_BACKLOG の再評価` は上記で前倒し実施済み**。本タスクでは (1) の可視化を入れたうえで、
**6 が妥当かを実測で再評価**すること（「安易に増やさない」原則は不変）。

読み上げは FIFO 直列（`playing` フラグ・`pump` 211 行〜）で、1 件の再生が終わるまで次に進まない。**実測に基づく試算**:

| 1 件の長さ | 読み上げ所要（VOICEVOX 日本語 ≒ 4.5〜6 文字/秒） | dev-mock（1800ms 間隔）でその間に届く数 | 破棄される数 |
| --- | --- | --- | --- |
| 290 文字（`dev-mock.ts` の長文枠・赤スパ本文上限相当） | **約 48〜64 秒** | 27〜38 件 | **7〜18 件** |
| 200 文字 | 約 33〜44 秒 | 18〜24 件 | 0〜4 件 |
| 60 文字（048 の既定上限） | 約 10〜13 秒 | 5〜7 件 | **0 件** |

→ **048（文字数上限）を入れるだけで長文起因の破棄はほぼ解消する**。ただし**バースト起因の破棄は残る**
（実チャットで毎秒 2 件が 20 秒続けば 40 件到着 → 20 件破棄）。また破棄されること自体が今は見えない。

⚠ **049 実装（2026-07-31）で上表の「届く数」の前提が変わった**。従来は `membership` / `gift` / `jewels` が
`text` 空で ⑤ 空判定に落ち**キューに載っていなかった**が、049 以降は要約文言が読まれるので載る。
**1 件あたりの長さは 048 の上限（既定 60）で頭打ち**なので、1 件の占有時間の上限は変わらない（増えるのは件数だけ）。

増分の内訳（**049 レビュー Q-3 で数え直して訂正**。当初「seq 7/9/13/14 の 4 件・約 +20%」と書いたが誤り）:

- **`seq 9`（jewels）は増分に数えない**。dev-mock だけが `text = "投げ銭ジュエル 🎁"` を入れているため
  **従来から dev では読まれていた**（049 で変わるのは読まれる内容だけ）。本番のみ無音だったのが本タスクの罠。
- **`seq 7 / 9 / 13 / 14` は同時に成立しない**。`dev-mock.ts` の `seq` は**両 provider 共通の単調カウンタ**で、
  各イベントは `seq % 20 === k` **かつ**特定 `source` を要求する。両 provider は同一間隔（1800ms）なので seq は
  厳密に交互＝**{7, 9, 13} は同じパリティ・14 は逆**。7/9/14 は youtube、13 は twitch を要求するため、
  **1 周期で発火するのは最大 2 件**。

| 構成 | 新たに読み上げ対象になる件（20 seq あたり） | 増分 |
| --- | --- | --- |
| 両接続・odd=youtube | seq 7（9 は既読・13/14 は不発） | **+1 件（+5%）** |
| 両接続・odd=twitch | seq 13, 14 | **+2 件（+10%）** |
| YouTube 単独 | seq 7, 14（9 は既読） | **+2 件（+10%）** |
| Twitch 単独 | seq 13（17 は既読） | **+1 件（+5%）** |

＝**dev-mock での実際の増加は +5〜10%**（seq 12 の combo 更新は `mergeComments` の `updated` なので従来どおり
載らない＝この点は当初の記述どおり正しい。`seenIds` も二重の防波堤になる）。

⚠ **dev-mock の比率は実データを代表しない**。本番では `membership` / `gift` / `jewels` が
**100% 無音 → 100% 読み上げ**に変わるので、**課金イベントの多い配信ほど増分は大きい**。
バースト起因の破棄を実測するときは dev-mock の数字ではなく**実配信での課金イベント比率**を根拠にすること。

### (2) 合成タイムアウト（詰まりを塞ぐ）—— ✅ **実装済み（2026-07-31）**

- [`ttsQueue.ts`](../../apps/desktop/src/features/comment-viewer/ttsQueue.ts) の `pump` で `synthesize` に **`AbortSignal` を渡す**
  （`AbortController` ＋ `setTimeout` の標準 API のみ＝**新規依存ゼロ**）。**既定 10 秒**（`SYNTH_TIMEOUT_MS`）。
  タイムアウトは **2 回の fetch と body 読みの合計**に掛かる（守りたい不変条件が「1 件が 10 秒以上詰まらない」ため）。
- タイムアウトしたら**その 1 件だけ諦めて次へ進む**（既存 catch と同じ作法・直列は止めない）。
  ⚠ **通常の合成失敗と区別しない**（通知を作らないので区別する意味が無く、abort は `AbortError` として
  既存 catch にそのまま落ちる＝分岐もフラグも増えない）。`onSkipped` は入れていない。
- ⚠ **塞いだのは「ENGINE が生きているのに応答しない」ケースだけ**。ENGINE 停止・クラッシュは接続拒否で
  即エラーになり既存の `engineBanner` ＋自動起動が担当するので、元から詰まらない（**通知が二重になる余地も無い**）。
- 「意図的に signal を渡さない」コメント（`pump` 内）は、**dispose 中断とタイムアウト中断は別目的**である旨に更新した
  （dispose 時は従来どおり中断しない＝`disposed` ガードで再生を抑止する設計は維持）。

### (2') 再生ストール（起票時に見えていなかった同型の穴）—— ✅ **実装済み（2026-07-31）**

- **再生中**に AudioContext が suspended になると `src.onended` が発火せず `playWav` が永久 pending になる
  （下記「経路3」のガードは**再生前しか見ない**ので素通りする）。合成タイムアウトと同じく**復帰不能な無音**。
- **時間では切らない**（まだ鳴っている音を打ち切ってしまう）。**`ctx.state` が running でなくなったこと**＝
  音が出ていないことを条件に打ち切る（1 Hz ポーリング・`PLAYBACK_STALL_CHECK_MS`）。
  `statechange` イベントを使わないのは、塞ぐ相手が「発火するはずの `onended` が発火しない」ケースだから。
- `playWav` に `signal` を足し、打ち切りでは **`stop()` ＋ `disconnect()` まで**行う（stop だけだと後の
  `ctx.resume()` で息を吹き返し、次の 1 件と**音が重なる**）。**reject ではなく resolve**（打ち切りは異常ではない）。

### (4) MAX_BACKLOG の再評価 —— ⚠ **保留（6 のまま・変更していない）**

- ⚠ **049 フォローアップで 20 → 6 に前倒し変更済み**。よってここで判断するのは「**6 が妥当か**」
  （起票時の「20 のままでよいか」は古い記述）。
- **上限導入で溢れにくくなっているはずなので、安易に増やさない**（増やすと「今のコメント」ではなく
  「数分前のコメント」を読み続ける、より悪い体験になる）。判定材料:
  - `MAX_BACKLOG=N` の最悪遅延 ≒ **(N+1)×10〜13 秒**（N=6 で 70〜91 秒）。
  - ⚠ **スキップ率は、流量が消費を上回る限り N を増やしても減らない**（遅延だけが伸びる）。
    「捨てられているから増やす」は誤り。**増やす価値があるのは取りこぼしが間欠的（バースト起因）なときだけ。**
- 変える場合は根拠（実測値）を [`docs/progress.md`](../progress.md) に残す。

## E2E（手動）確認チェックリスト

> ⚠ **可視化（通知 UI）は不採用**なので、**画面には何も出ない**。判定は**耳**と **DevTools Console / Network**で行う。
> 起票時の「スキップ通知が出るか」という記述は無効（本節はその訂正を兼ねる）。
>
> **なぜ手動なのか**: 以下はいずれも「実 VOICEVOX ENGINE の応答時間」「WKWebView の AudioContext が本当に
> suspended になるか」「`stop()`＋`disconnect()` した source が実 Web Audio で本当に蘇らないか」に依存する。
> 偽 AudioContext とモック `fetch` では**原理的に観測できない**（ユニットで固定したのは*契約*であって*実挙動*ではない）。

### 準備

1. `COMMENT_SIDECAR_MOCK=1 pnpm tauri dev` で起動。sidecar の stderr に
   `[comment-sidecar] MOCK MODE enabled` が出ていることを確認する（出ていなければ env が sidecar まで届いていない）。
2. コメントビューアの窓で **DevTools を開き、Console と Network を両方見られるようにする**。
   Console は `TTS` でフィルタ、Network は `50021` でフィルタしておく。
   ⚠ **ここで「Network パネルにリクエストが記録されること」を先に確認する**（適当なコメントを 1 件流して
   `/audio_query` が出るか）。E2E-1（Time の合計）と E2E-2（`(canceled)` か `failed` か）は
   **Network が読めることに全面的に依存**しており、読めないとこの 2 つが丸ごと実行不能になる
   ——タイムアウトと通常の合成失敗を意図的に同じログにした設計の運用コストがここに出る。
   ⚠ WKWebView で DevTools が開けない場合は、`tauri.conf.json` の devtools 設定か Safari の
   「開発」メニュー経由（Web Inspector）を使う。**どうしても読めないなら E2E-1 は
   「1 件目が読まれるか」の耳判定だけに縮退**させ、実測値の取得は別途行うこと。
3. VOICEVOX ENGINE の PID を控える（`pgrep -f -i voicevox`）。E2E-6 で使う。

### E2E-1【最優先】ENGINE 起動直後の 1 件目が読まれるか（`SYNTH_TIMEOUT_MS` が短すぎないか）

- **何を見るか**: モデルロードを含む**初回合成が 10 秒を超えないか**。超えていると「起動して最初のコメント
  だけ読まれない」という、通知が無い以上いちばん原因に辿り着きにくい形で出る。
- **手順**: VOICEVOX ENGINE を**起動した直後**（モデル未ロード）に、読み上げ ON でコメントを 1 件だけ流す。
- **期待**: 1 件目が読まれる。Network の `/audio_query` ＋ `/synthesis` の **Time の合計が 10 秒未満**。
- **失敗したら**: Console に `VOICEVOX 読み上げに失敗しました` が出て 1 件目が無音になる。Network で
  該当リクエストが **`(canceled)`** なら合成タイムアウト＝`SYNTH_TIMEOUT_MS` を実測値ベースで伸ばす。
- **合わせて記録する**: 定常状態での `/audio_query` ＋ `/synthesis` の実測合計（**この値が無いままなのが
  現在の最大の弱点**。レビュー Q-2）。

### E2E-2 通常運用で読み上げが飛ばないか

- **何を見るか**: 10 秒が**恒常的に**発動していないか。
- **手順**: 30 分〜1 時間、mock または実配信を流しっぱなしにする。
- **期待**: Console の `VOICEVOX 読み上げに失敗しました` が**0 件、または明確な原因があるときだけ**。
- ⚠ **タイムアウトと通常の合成失敗は同じログ**（意図的に区別していない）。出たときは **Network で該当行を見て
  `(canceled)`＝タイムアウト／`failed`＝接続拒否**を判別する。これが区別しない設計の運用上のコスト。

### E2E-3【050 の核心】背面に回してから戻すと読み上げが再開するか

- **何を見るか**: **B（再生ストール）と経路3 の発生有無をここで確定させる**。macOS の WKWebView で
  AudioContext が実際に suspended になるのかは未確認で、ならないなら (3) は永久に不要と結論できる。
- **手順**: 読み上げ中に別アプリへ切り替え → 30 秒放置 → コメントビューアに戻す。
- **期待**: 戻したあと、**次のコメントから読み上げが再開する**（永久無音にならない）。
- **Console で読み取ること**:
  - `TTS: 再生中に AudioContext が停止したため、この 1 件を打ち切りました` → **B が発動**（＝suspended になる環境）。
  - `TTS: AudioContext が running でないため、この 1 件の読み上げをスキップしました` → **経路3 が発動**。
  - **どちらも出ない** → macOS では suspended にならない＝**(3) は不要**と確定でき、050 の積み残しが 1 つ消える。

### E2E-4 打ち切った音が後から鳴り出さないか（音が重ならない）

- **何を見るか**: `stop()` ＋ `disconnect()` の**実効果**。`stop()` だけだと `ctx.resume()` の瞬間に source が
  蘇り、既に次を再生しているキューと音が重なる。**偽 AudioContext では絶対に観測できない**。
- **手順**: E2E-3 で「B が発動」した直後、**戻した瞬間の 2〜3 秒に耳を澄ます**。
- **期待**: 打ち切られたコメントの**続きが鳴らない**／次のコメントと**重ならない**。
- **失敗したら**: `playWav` の abort で `disconnect()` に到達していない（＝Q-1 の防御が効いていない可能性）。

### E2E-5 ENGINE 停止時は 1 件で固まらず、起動誘導バナーが出るか

- **何を見るか**: 「停止・クラッシュは接続拒否で**即エラー**＝既存バナーの担当」という 050 の前提が正しいか。
- **手順**: VOICEVOX ENGINE を落とした状態で読み上げ ON → コメントを流す。
- **期待**: 起動誘導バナーが出る。Console のエラーは**即座に**出る（**10 秒待たない**＝タイムアウト経路に
  入っていないこと）。読み上げは無音だが、キューが詰まって「以後ずっと無音」にはならない。

### E2E-6 ENGINE が「無反応」のときの挙動（051 の必要性の確認）

- **何を見るか**: `checkEngineRunning` にタイムアウトが無い既知問題（**未修正**）の実害。
- **手順**: `kill -STOP <VOICEVOX の PID>` でプロセスを**サスペンド**（落とすのではなく無反応にする）
  → コメントを流す → 挙動を観察 → **確認後は必ず `kill -CONT <PID>` で戻す**。
- **期待（現状の仕様）**: 読み上げは 10 秒で 1 件を諦めて次へ進む（＝050 A が効いている）。
  一方で**起動誘導バナーは出ない**（`GET /version` も返らないため）。Network に `/version` の
  pending が 5 秒ごとに積み上がる。
- **これが再現したら**: 051 の起票が正しかったことの確認。読み上げ側は治っているがユーザーには
  何も見えない、という状態が実在する。

### E2E-7 ウィンドウを閉じたとき（dispose）に音が残らないか

- **何を見るか**: 今回入れた「dispose 中は打ち切りログを出さない」と、in-flight 再生の後始末。
- **手順**: 読み上げの**最中**にコメントビューアの窓を閉じる。
- **期待**: 音が即止まる。Console に
  `TTS: 再生中に AudioContext が停止したため…` が**出ない**（正常な後始末をストールとして記録しない）。

### E2E-8 `MAX_BACKLOG=6` の追従感

- **手順**: 高流量（mock は 1.8 秒に 1 件）で、**画面に出てから読まれるまでの遅延**をストップウォッチで測る。
- **期待**: **70〜91 秒以内**（＝(N+1)×10〜13 秒）。
- ⚠ **「捨てられているから増やす」は誤り**。流量が消費を上回る限り N を増やしてもスキップ率は減らず、
  遅延だけが伸びる。増やす価値があるのは**取りこぼしが間欠的（バースト起因）のときだけ**。

### E2E-9 loopback fetch が WKWebView の ATS を通るか（032c-c からの積み残し）

- **手順**: Network で `GET /version` を確認する。
- **期待**: 200 が返る。ブロックされる場合のみ `tauri.conf.json` の ATS/接続許可を**最小調整**する
  （宛先は 50021 loopback 限定を維持）。通れば変更不要。

### E2E-10 DevTools に読み上げ全文が写ることの確認（レビュー S-1・修正ではなく運用注意）

- **手順**: Network の `/audio_query` を 1 件選び、Request URL を見る。
- **期待（＝そうなっているはず）**: `?text=` に**コメント本文と、課金イベントなら投稿者の表示名**が入っている。
- **意味**: これはブラウザ機能でアプリのログではないので §9 違反ではないが、**診断のスクリーンショットを
  共有するときに第三者の氏名が写る**。共有前にマスクすること。
