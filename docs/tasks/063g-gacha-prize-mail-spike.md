## 目的

依頼者の要望（2026-08-30・**原文**）:

> ガチャについて、可能であれば、特定の商品が当たった人にメールを送るようにしたい。配信者さんによっては、
> 大当たりの景品にスマホ壁紙等を設定している人がおり、おそらく現状はサマリーで確認してその人の Twitter
> アカウントか何かに商品を渡しているのだと思う。ガチャテンプレの設定で、その人のメールアドレスに商品と
> なっているスマホ壁紙等の画像を自動送信するようにしたい。ただし、**送れるのは画像のみで良い**。ここに
> ファイルや文字列を送れるようにすると**スパムにつながるかもしれない**ため。文言はテンプレートで、
> 〇〇さんからガチャの景品が届きました！とかで良いと思う。**可能かどうかの技術調査から行いたい。
> できればクラウドサーバーは使いたくない。**

⇒ 本タスクは **「できるか／どの形なら安全にできるか」を決めるところまで**を担当する。
⚠⚠ **「やらない」という結論も正当な成果物である**（063t が「4 つのうち 1 つしかできない」と
確定させたのと同じ性質のタスク）。

## ⚠⚠ なぜ記録（063h）より先なのか

理由は 2 つあり、**どちらも「後からでは直せない」**種類のものである。

1. ⚠⚠⚠ **結論が [063h](063h-gacha-draw-recording.md) のテーブル定義に効く。**
   宛先の入手経路が「**チャネポの引き換え入力**」に決まった場合、
   「どの引き換えがこの抽選を起こしたか」＝ **引き金になったコメントの id** を
   `gacha_draws` が持っていないと、**後からメールアドレスに辿り着けない**。
   ⚠ このアプリに**マイグレーション基盤は無い**（各 `repository::init` が冪等 DDL を撃つだけで、
   列の後付けは `ensure_column` の手作業）。⇒ **列は最初から決めておくほうが安い。**
2. **「やらない」と決まったときに、063h の設計から余分な考慮を落とせる。**
   逆順にすると、使われないかもしれない列と「宛先解決」の余地を抱えたまま
   保存ポリシーの `security-review` を通すことになる。

⚠ 逆に **063h・063i の実装そのものは本タスクの結論を待たない**（記録と表示は要望①として独立している）。
待つのは**列の確定**だけである。

## 前提（⚠ 実コードで確認済み・2026-08-30）

### (a) 当選者のメールアドレスは、プラットフォームからは取れない（⚠ 裏取りは本タスクの最初の作業）

Twitch の `user:read:email` は **認証した本人（＝配信者）のメールアドレス**を返すスコープで、
**視聴者のメールアドレスを返す API は無い**（YouTube も同様）というのが現時点の前提である。
⚠⚠ **これは実装済みコードから確認できる事実ではなく、公式ドキュメントで裏を取るべき前提**なので、
**問い 1 の最初の作業として明示的に確認し、結果を本ファイルへ書く**こと。

⇒ ⚠⚠⚠ **この前提が正しいなら、宛先は「視聴者本人に打ってもらう」以外の入手経路が存在しない。**
本 spike の中心はそこから先＝**打ってもらった文字列をどう安全に扱うか**である。

### (b) チャネポの引き換え入力は、すでにアプリの中を流れている（063e）

- Twitch の `user_input`（＝視聴者が引き換え時に打つ文字列）は、sidecar の mapper で
  **コメントの本文 `text` にそのまま入る**
  （[comment.mapper.ts:275](../../apps/comment-sidecar/vendor/comment-fetcher/src/adapters/twitch/mapper/comment.mapper.ts#L275)）。
- 種別は `CommentEventType` の **`channelpoint`**
  （[CommentEventType.ts](../../apps/desktop/src/features/comment-viewer/bindings/CommentEventType.ts)）。
- 報酬名は `rewardTitle` として別に載っており、**報酬ごとにガチャを出し分けられる**（063e 段 3）。

⇒ **新規の egress も新規スコープも足さずに、視聴者の打った文字列を受け取れる**——ここまでは既にできている。

### (c) ⚠⚠⚠ その本文が流れる先は、実測で 6 つある

| # | 経路 | 本文が出るか | 根拠（実コード） | ⚠ 配信に乗るか |
|---|---|---|---|---|
| 1 | コメビュ窓の一覧 | **出る**（「チャンネルポイント」バッジ付き） | [CommentList.tsx:324](../../apps/desktop/src/screens/comment-viewer/CommentList.tsx#L324) | 配信者の画面のみ（⚠ **画面共有・キャプチャ範囲を誤ると乗る**） |
| 2 | コメントオーバーレイ（OBS） | ⚠ **出ない** | [CommentList.tsx:503](../../apps/desktop/src/screens/comment-viewer/CommentList.tsx#L503)（`renderOverlayItem` が `channelpoint` で早期 return） | **乗らない** |
| 3 | 固定コメント＋固定オーバーレイ窓 | ⚠⚠ **配信者が固定すれば出る** | [pinnedComments.ts:77](../../apps/desktop/src/features/comment-viewer/pinnedComments.ts#L77)（`channelpoint: true`） | ⚠⚠ **乗る**（`pinned-overlay` は OBS キャプチャ対象） |
| 4 | 読み上げ（VOICEVOX） | ⚠⚠⚠ **読まれる** | `composeEventMessage` は `channelpoint` に分岐が無く `default: null`（[viewerFormat.ts:308](../../apps/desktop/src/screens/comment-viewer/viewerFormat.ts#L308)）⇒ `composeSpeechText` が **`c.text` をそのまま返す**（[speechText.ts:165](../../apps/desktop/src/screens/comment-viewer/speechText.ts#L165)） | ⚠⚠⚠ **音声として乗る** |
| 5 | 視聴者メモリ DB | **保存される**（`viewer_comments.text`） | `recordOrBufferComments`（[CommentViewerApp.tsx:1500](../../apps/desktop/src/screens/comment-viewer/CommentViewerApp.tsx#L1500)） | 乗らない（⚠ ただし**端末に残る**＝§9 の対象） |
| 6 | エフェクトのキーワード条件 | 照合に使われる | `effectAssignments.ts` の照合 | 乗らない（本文は OBS へ渡らない＝`EffectMatch` に本文の場所が型として無い） |

⇒ ⚠⚠⚠ **「引き換え時にメールアドレスを打ってもらう」を素で作ると、少なくとも 3 と 4 で配信に出る。**
特に **4（読み上げ）は既定で有効になりうる経路で、配信者が気づく手掛かりが音声しかない**。

### (d) 送信機構まわりの既存の資産と制約

- **Rust に HTTP/async を持ち込まない方針**（`keyring` / `csv` / `rodio` はいずれも
  「**同期 API・tokio を引かない**」を理由に採用されている）。
  ⚠ 例外は `tauri-plugin-updater` ただ 1 つで、`docs/security.md` §1 に
  「**正面からの例外**」と明記されている。
- **OS キーチェーンは既にある**（`keyring` crate・Twitch/YouTube のトークン保存）。
- **ファイル取り込みの先例がある**: `app_data_dir/themes/<uuid>.css`
  （[overlay_theme/service.rs](../../apps/desktop/src-tauri/src/overlay_theme/service.rs)）＝
  **パスを frontend から受け取らない**・保存先は固定形のみ、という §5 の例外の作り方。
- **sidecar の allow-list は `fetch` / `ws` / gRPC にしか掛からない**
  （[host-guard.ts](../../apps/comment-sidecar/src/host-guard.ts)）。⚠ **生の TCP/TLS は見ていない。**
- `tauri-plugin-opener` は既に依存にある（`.eml` 案で使う）。

## 調べること（問い 5 つ）

⚠ **各問いは「結論」と「却下した案とその理由」をセットで書くこと**（063s / 063t と同じ様式）。

### 問い 1 ⚠⚠⚠ 宛先（メールアドレス）の入手経路 — **本命はチャネポ入力**

依頼者の指示（2026-08-30）: **「チャネポ入力を本命に調べる」**。

**出すべき結論**:

1. 前提 (a) の裏取り（公式ドキュメントの参照付き）。
2. ⚠⚠⚠ **上の表 (c) を「全数」にすること**——本 spike の**最重要成果物**である。
   6 経路は**実測で見つかったもの**であって、網羅の証明ではない。
   ⚠ 探し方まで書くこと（例: `CommentViewDto` の `text` を読む箇所を機械的に洗う／
   `viewer_comments.text` を読む Rust 側の経路／localStorage に本文が載るキー）。
3. 各経路に対する**マスクの入れ方**と、⚠⚠ **「漏れたら気づけるか」**。
   - ⚠ マスクを **N か所に分散させる案は原則却下**（1 か所漏れたら事故で、しかも
     配信に出るまで誰も気づかない）。⇒ **単一のチョークポイントを作れるか**が判定軸になる。
   - 候補として検討すること: **報酬名で「これは宛先入力の報酬だ」と判定し、
     取り込みの時点（sidecar か Rust の記録層）で本文を落とす**形
     ——落とせば 1〜6 のすべてが同時に塞がる。⚠ ただし
     **落とした本文をどこで拾うのか**（＝送信に使う値の置き場）が別問題として残る。
4. **対案を同じ土俵で評価すること**（⚠ 本命が危険と分かった場合の受け皿）:
   - **配信者の手入力** … [063i](063i-gacha-summary-view.md) の当選一覧の行から
     「メールで送る」を押し、アドレスは配信者が貼る。**事故が構造的に起きない**代わりに
     「**自動送信**」ではなくなる。
   - **端末内に受付ページを立てる** … クラウドではないが**サーバーである**
     （ポート開放・URL の配布・未認証の口が増える）。⚠ 却下候補として理由まで書く。
5. ⚠ **視聴者側の体験**も書くこと（引き換え欄にメールアドレスを打つのは、視聴者にとって
   **モデレーターや他の視聴者に見られる**行為ではないか＝Twitch 側でその文字列がどこに出るのか）。

### 問い 2 送信機構 — **SMTP 直送と `.eml` 生成を同じ重さで**

依頼者の指示（2026-08-30）: **「両方を同じ重さで調べる」**。

| 判定軸 | 案 A: Rust から SMTP 直送（`lettre` 等） | 案 B: `.eml` を書き出して既定のメールクライアントで開く |
|---|---|---|
| 「自動送信」になるか | **なる** | ⚠ **ならない**（人が送信ボタンを押す） |
| 新規 egress | ⚠⚠⚠ **増える。しかも §1 の allow-list が作れない**（宛先ホストがユーザー設定） | **ゼロ** |
| 資格情報 | SMTP のユーザー名／パスワード（`keyring` へ）⚠ **アプリパスワード運用の説明が要る** | **不要** |
| 依存 | ⚠ 新規 crate ＋ TLS スタック。⚠⚠ **tokio を引かないか実測が要る** | ほぼゼロ（`tauri-plugin-opener` は既存） |
| 失敗の見え方 | 送信失敗を画面に出す設計が要る（061a Q-1 / 063f と同じ規律） | 開けなければ即わかる |
| ⚠ 未知 | Gmail 等のアプリパスワード可否・送信数上限・迷惑メール判定 | ⚠ **各メールクライアントが添付付き `.eml` を開けるか**（macOS Mail / Outlook / Thunderbird） |

**出すべき結論**:

- 案 A を採るなら: 使う crate と **`cargo tree` の実測**（⚠ **tokio / async ランタイムを引かないこと**が
  採用条件。`rodio` / `csv` / `keyring` と同じ基準）、TLS スタック（⚠ **`rustls` へ寄せられるか**
  ——`tauri-plugin-updater` が既に rustls を引いているので、`native-tls`/OpenSSL を増やさないこと）、
  §1 に書く例外の**文面案**（⚠ **allow-list が作れないことを正面から書く**）。
- 案 B を採るなら: **`.eml`（RFC5322 + MIME）を手書きするのか crate を使うのか**、
  実際に 3 クライアントで**添付付きで開けたか**の実測、書き出し先（`app_data_dir` 配下・§5）、
  ⚠ **書き出したファイルを消すのは誰か**（アドレスが端末に残る＝§9）。
- ⚠ **却下候補: sidecar（Node）に寄せる案。** 理由の候補＝
  ①**コメビュ窓を開いている間しか生きていない**（送信の契機は当選なので同時ではあるが、再送や
  後追い送信ができない）②単一ファイル SEA なので native な依存を持てない
  ③ **host-guard は fetch/ws しか見ておらず、SMTP は素通りする**＝
  「通信は sidecar に封じ込める」という既存の構図の**根拠が成立しない**。
- ⚠ **どちらの案でも `mailto:` は使えない**（**添付ができない**）。この点は最初に潰しておくこと。

### 問い 3 景品画像の置き場と検証

- 置き場の第一候補は **`app_data_dir/gacha-prizes/<uuid>.<ext>`**
  （[overlay_theme](../../apps/desktop/src-tauri/src/overlay_theme/service.rs) の CSS 取り込みと同型＝
  ⚠ **パスを frontend から受け取らない**・保存先は固定形のみ）。
- 検証要件は `docs/security.md` §8 の **061c（エフェクトテンプレートの検証要件）**を参照して、
  **拡張子だけで判定しない**（マジックバイト）・**サイズ上限**・**枚数上限**を決めること。
- ⚠ 決めること: **1 景品に 1 枚か**／**ガチャ定義は localStorage にある**
  （`stream-dock.obs-effects.gachas`・[overlaySettings.ts:502](../../apps/desktop/src/features/comment-viewer/overlaySettings.ts#L502)）ので、
  **画像の実体は Rust 管理・localStorage には id だけ**という形になるはず。その整合をどう保つか
  （⚠ **id だけ残って実体が無い**／**実体だけ残って参照が無い**の 2 方向）。

### 問い 4 スパムにしないための壁

依頼者が要望の中で自分から挙げている制約（**画像のみ・文言はテンプレート**）を、
**運用の約束ではなく構造で**成立させられるかを決める。

最低限、次のどれを構造で持てるかを書くこと:

- 本文は**テンプレート固定**（⚠ ユーザーの自由入力を本文に入れない＝
  `docs/security.md` §1 の 063f 追補の再修正トリガー ③ と同じ考え方）。
- 添付は**アプリが管理している 1 ファイルだけ**（任意のパスを渡せない）。
- 1 通あたりの宛先は 1 件・**同報しない**。
- **レート上限**（⚠ 置き場所は「未認証の口から回避できない側」——063f のスロットルが
  **frontend ではなく sidecar にある**理由と同じ議論をやり直すこと）。
- **既定 OFF の同意**（⚠ 063f で同意が 1 枚になった経緯＝§1 の 063f 追補を読むこと。
  「**同意のトグルをこれ以上減らさない**」という制約が既にある）。
- ⚠⚠ **送る前に人が確認する画面を挟むか**（＝「自動送信」をどこまで自動にするか）。

### 問い 5 §1 / §9 への影響と、追補の**文面案**

- §1: 新規 egress（案 A の場合）。⚠⚠ **allow-list が作れない初めての宛先**になることを正面から書く。
- §9: **メールアドレスは、いまアプリが扱っていない種類の個人データである。**
  - 保存するのか（「送信済みか」を画面に出すには**何らかの記録が要る**）。
  - 保存するなら**削除連動**（`delete_viewer` / `clear_viewers` の対象に入るか）。
  - ⚠ **ログに出さない**（件数も）。
  - ⚠ 063f 追補が「**送ったものの記録を作らないこと**」と書いた理由（取り消せない公開の記録が
    端末にも残る）と、本件（**宛先の記録が無いと二重送信・未送信が判別できない**）は
    **利害が逆を向く**。⇒ ⚠⚠ **どちらを採るかを、理由付きで決めること。**
- ⚠ **追補は本文案まで書く**（実装タスクで書き下ろすのではなく、spike の成果物として持つ）。
  そのほうが「実装してから書けないと分かる」を避けられる。
