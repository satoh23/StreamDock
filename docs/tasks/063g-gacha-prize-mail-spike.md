## ⚠⚠⚠ 結論（先に書く）

**ガチャ景品の自動配布は実装しない。**
要望①（**誰が何を当てたかを配信サマリーで見る**）は [063h](063h-gacha-draw-recording.md) ＋
[063i](063i-gacha-summary-view.md) で**独立して完成する**ので、**そこから先は配信者の手作業に委ねる**。

⚠⚠ **技術的にできなかったのではない。** 調べた結果、次の 3 つが同時に成立してしまい、
**どの案も依頼者の受け入れ条件のどれかを必ず割る**ことが分かった。

1. ⚠⚠⚠ **視聴者のメールアドレスを取得する API は存在しない**（一次ソースで確定・下記 (1)）。
   ⇒ 宛先は **視聴者本人に打たせる**しかない。
2. ⚠⚠⚠ **打たせると、その文字列は Twitch 側で第三者に見える**（引き換えキューはモデレーターが開ける）。
   ⚠ StreamDock は `channel:read:redemptions` の**読み取り専用**なので**消化して消すこともできない**。
   ⇒ 依頼者の判断: **「メアドを誰でも見える場所に書き込ませるのは論外」**。
3. ⚠⚠⚠ **メール以外で「そのアカウントの本人だけ」に画像を届ける手段が無い。**
   Twitch のウィスパーは**テキストのみ**（添付不可）でリンクしか送れず、
   **リンクは転送できる**。⚠ 転送を防ぐ唯一の方法は「ページ側で Twitch ログインさせる」ことだが、
   それには**サーバーが要る**＝要望「**できればクラウドサーバーは使いたくない**」と正面衝突する。

⚠⚠ **「そのユーザーしか知り得ない情報をパスワードにする」案も原理的に成立しない**（下記 (1-e)）。

## 目的（据え置き）

依頼者の要望（2026-08-30・**原文**）:

> ガチャについて、可能であれば、特定の商品が当たった人にメールを送るようにしたい。配信者さんによっては、
> 大当たりの景品にスマホ壁紙等を設定している人がおり、おそらく現状はサマリーで確認してその人の Twitter
> アカウントか何かに商品を渡しているのだと思う。ガチャテンプレの設定で、その人のメールアドレスに商品と
> なっているスマホ壁紙等の画像を自動送信するようにしたい。ただし、**送れるのは画像のみで良い**。ここに
> ファイルや文字列を送れるようにすると**スパムにつながるかもしれない**ため。文言はテンプレートで、
> 〇〇さんからガチャの景品が届きました！とかで良いと思う。**可能かどうかの技術調査から行いたい。
> できればクラウドサーバーは使いたくない。**

⚠ 調査の途中で、依頼者から**要望の範囲を広げる指示**が 2 回入っている（時系列は下記「判断の経緯」）。

## (1) 問い 1: 宛先の入手経路 — 結論 **経路が無い**

### (1-a) ⚠⚠⚠ 視聴者のメールアドレスを返す API は存在しない（**一次ソースで確定**）

| 事実 | 出典（一次） |
|---|---|
| 「ユーザーの User リソースを取るのに許可は要らないが、**そこにメールアドレスを含めるにはそのユーザーの許可が要る**」（原文: *"you don't need permission to get a user's User resource but you do need their permission to include their email address with the resource."*） | Twitch: `dev.twitch.tv/docs/authentication/` |
| `user:read:email` ＝「View a user's email address.」。⚠ **email に触れるスコープはこれ 1 つだけ** | Twitch: `dev.twitch.tv/docs/authentication/scopes/` |
| `liveChatMessage.authorDetails` は `channelId` / `channelUrl` / `displayName` / `profileImageUrl` / `isVerified` / `isChatOwner` / `isChatSponsor` / `isChatModerator` の **8 つのみ**。⚠ **email フィールドは存在しない** | YouTube: `developers.google.com/youtube/v3/live/docs/liveChatMessages` |

⇒ ⚠⚠ **視聴者が StreamDock に OAuth 認可しない限りアドレスは手に入らず、そんな経路は無い。**
⚠ **タスクファイルの前提 (a) は正しかった**（本節でその裏取りを完了した）。

### (1-b) ⚠⚠⚠ 却下: チャネポの引き換え入力（`user_input`）を宛先にする

**アプリの中は塞げる。塞げないのは Twitch 側である。**

- ✅ **アプリ内の 11 面は、単一のチョークポイントで同時に塞げることを確認した**（下記 (2) が全数リスト）。
  置き場は **sidecar の `wire.ts`（`toCanonicalComment`）／`index.ts` の `broadcastMessage` 直前**で、
  ⚠ **vendor を 1 行も触らずに済む**。⚠⚠ **frontend でも Rust でも駄目**である
  （どちらも**未認証 loopback WS のブロードキャストより下流**だから＝(2) の面 1）。
- ✅ **チャネポでガチャを回す経路は `text` を見ていない**ので、落としてもガチャは 1 つも壊れない
  （063e 段 3-c で条件が `{ type:"channelpoint"; rewardTitle }` になった）。壊れるのは
  「チャネポの本文にキーワード条件を当てる」使い方だけ。
- ⚠⚠⚠ **それでも却下したのは、次の 2 つがアプリの外にあるから**:
  1. **引き換えは Twitch の「引き換えリクエストキュー」に残り、モデレーターが Mod View から見られる。**
     ⚠⚠ **StreamDock は `channel:read:redemptions`（読み取り専用）しか持たず、
     `channel:manage:redemptions` は「できないことを、できなくしておく」という 063e の明文の決定で
     取らないと決めている**（`twitch-config.ts`）。⇒ **消化して消すことができない。**
     ⚠ キューを飛ばす設定（`should_redemptions_skip_request_queue`）は**報酬を作る側の設定**で、
     StreamDock は報酬を作れない ⇒ **運用の約束にしかならず、構造にできない。**
  2. ⚠ **打った文字列が公開チャットに出るかは未確定**（二次ソースは複数一致で「出る」・**一次確認は未実施**）。
     ⚠⚠ **依頼者の環境ではチャンネルポイントを有効化できないので、この一次確認ができない**（063e 段 1-b の記録）。

⇒ 依頼者の判断（2026-08-30）: **「メアドを誰でも見える場所に書き込ませるのは論外」**。

### (1-c) ⚠ 却下: 配信者の手入力（半自動）

[063i](063i-gacha-summary-view.md) の当選一覧の行から「メールで送る」を押し、**アドレスは配信者が貼る**案。
**事故が構造的に起きない**（アドレスがアプリを流れない）代わりに「自動送信」ではなくなる。

⇒ 依頼者の判断（2026-08-30）: **「不便すぎる。ないほうがマシレベル」**。⚠ **却下。**

### (1-d) ⚠ 却下: 端末内に受付ページを立てる

クラウドではないが**サーバーである**。066 が「未認証の loopback WS」をチケットで塞いだ議論が
そのまま再燃し、⚠⚠ **しかも今度は入ってくるのが個人データ**である。
加えて **URL の配布手段が無い**（結局チャットに貼る＝公開の口）。⚠ **却下。**

### (1-e) ⚠⚠⚠ 却下: 「そのユーザーしか知り得ない情報」をパスワードにする

依頼者の案（2026-08-30）: ダウンロードページを作り、**視聴者本人しか知り得ない情報**を
パスワードとして入力させ、本人だけがダウンロードできるようにする。

**2 つの理由で原理的に成立しない。**

**① そんな情報が存在しない。** StreamDock が視聴者について知り得るものは、
**すべて公開情報か取得不可能かのどちらか**である:

| 候補 | 判定 |
|---|---|
| Twitch のユーザー ID | ⚠ **公開**（上記 (1-a) の一次引用がそのまま根拠＝「User リソースを取るのに許可は要らない」） |
| ログイン名・表示名 | 公開 |
| アカウント作成日（`created_at`） | 公開 |
| サブスク月数・バッジ | ⚠ **チャット欄のバッジで見える** |
| チャンネルポイント残高 | ⚠ **どの API でも取得できない**（StreamDock 側が知り得ない） |
| メールアドレス | 取得不可（(1-a)） |
| 引き換え時に打った文字列 | ⚠ **モデレーターにも見える**（＝(1-b) で却下した案そのもの） |

**② パスワード方式は循環する。** ランダムなパスワードを生成しても、
**それを本人にだけ届ける経路が必要**になる。

- その経路があるなら ⇒ **パスワードではなく景品リンクをそこへ流せばよい**（＝(3-c) のウィスパー案）。
- その経路が無いなら ⇒ **パスワードも届けられない**。

⇒ ⚠⚠ **パスワードページがウィスパー案より良くなることは構造上ありえない。**

**③ 転送を防げる唯一の方法はサーバーを要求する。** 本当に防ぎたいのは
「当選者がリンクを他人に渡す」ことだが、それを防げるのは
**「ページ側で Twitch ログインさせる」** ただ 1 つ（アカウントごと渡さない限り転送できないため）。
⚠ OAuth の検証と当選者リストの突き合わせを**利用者が書き換えられない場所**でやる必要があるので、
**サーバーが要る**。⚠⚠ 静的ページに当選者リストを埋め込む形は、
**ページのソースを読めば中身が全部見える**ので成立しない。
（Twitch Extensions ならプラットフォーム側の仕組みで本人確認できるが、
**公開審査つきのホスティング前提**なので同じ結論になる。）

⇒ 要望「**できればクラウドサーバーは使いたくない**」と正面衝突する。⚠ **却下。**

### (1-f) 視聴者側の体験（⚠ 記録として残す）

チャネポ入力を採った場合、視聴者は次を強いられる。**採らないと決めた根拠の一部**なので残す。

- ⚠ **最低 1 回はメールアドレスを打つ**（アカウントからは取れないため・(1-a)）。
- ⚠⚠ 打った文字列は **引き換えキューに残り、モデレーターが見られる**（(1-b)）。
- ⚠ 公開チャットに出るかは**未確定**（(1-b)）。
- ⚠⚠⚠ **Twitch 専用**——YouTube にチャンネルポイントに相当する機能が無いので、
  **YouTube の視聴者はこの機能を一切使えない**（063e が「YouTube 側は 1 文字も変えていない」と
  書いているのと同じ理由）。

### (2-a) 探し方（⚠ **6 軸。「なぜ全数と言えるか」つき**）

⚠⚠ **7 面が出発点であって網羅の証明ではなかった**ことは実際に起きた
（視聴者詳細パネルの 1 本は 2026-08-30 の見直しで初めて出てきた）。⇒ **機械的に洗う手順を残す。**

**軸 1: 型から辿る**

```bash
grep -rn "\.text\b" apps/desktop/src --include="*.ts" --include="*.tsx" | grep -v "\.test\."
```

⚠ **全数の根拠**: 本文を持つ型は **`CommentViewDto.text` / `PinnedComment.text` /
`ViewerCommentRecord.text` / `EffectMatchInput.text` の 4 つだけ**で、いずれもプロパティ名が `text`。
分割代入（`const { text } = c`）も同じ grep に掛かる。
⚠⚠ **名前が変わって grep から消える経路は 3 つだけ**で、いずれも「フィールドを明示列挙する変換関数」
＝ `toPinned`（`pinnedComments.ts`）／`toCanonicalComment`（sidecar の `wire.ts`）／
`row_to_comment`（`viewer_memory/repository.rs`）。**3 つとも `text:` のまま**で改名は起きていない。

**軸 2: DB の列から辿る**

```bash

```

⚠ **全数の根拠**: `text` 列を SELECT するのは定数 `VIEWER_COMMENT_COLUMNS` **1 つだけ**で、
使うのは `list_comments` とテストのみ。⇒ **DB から本文を読み出す経路は 1 本しか無い。**
⚠ `stream_summary` は同じテーブルを見るが `text: String::new()` を置いており、列を読んでいない。


⚠ **全数の根拠**: 25 キーをすべて目視した。本文が載るのは `PINNED_COMMENTS_KEY` の **1 つだけ**
（他はトグル値・id・ユーザー自身の設定値）。

**軸 4: 窓・プロセスの外へ出る口**

```bash

grep -rn "fetch(" apps/desktop/src/features/comment-viewer
```

⚠ **全数の根拠**: 窓間 emit は **2 本しか無い**（ガチャステージ結果・アプリ更新の進捗）。
sidecar → 窓は `broadcastMessage` / `sendToClient` の 2 本。
frontend からの外向き fetch はアバター取得と VOICEVOX のみ。

**軸 5: ログ・診断・クリップボード**

```bash
grep -rn "console.log\|logInfo\|log_command_err" apps/desktop/src apps/comment-sidecar/src apps/desktop/src-tauri/src
grep -rn "clipboard" apps/desktop/src
```

`GachaFireDetail` / `EffectMatch` / `EffectFireResult` / `StreamSummary` / `RaidRecord` に
**`text` フィールドが存在しない**ことを型定義で直接確認する。
⇒ 「たまたま渡していない」ではなく「**渡す場所が無い**」。

## (3) 問い 2: 送信・配布機構 — 結論 **どれも採らない**

### (3-a) ⚠ 案 A（Rust から SMTP 直送・`lettre`）: **依存は問題なかった。§1 で落ちた**

⚠⚠⚠ **タスクファイルの当初の懸念（tokio を引くか）は実測で解消した。**
リポジトリ外の捨てプロジェクトで `lettre 0.11` を
`default-features = false, features = ["smtp-transport", "rustls-tls", "builder", "hostname"]` で実測:

| 判定軸 | 実測結果 |
|---|---|
| ① 新しい async ランタイムを増やさない | ✅ **`cargo tree -i tokio` が "nothing to print"**。`async-std` / `smol` も不在 |
| ② `native-tls` / `openssl` を増やさない | ✅ **どれも不在**。TLS は `rustls 0.23` ＋ `ring 0.17`（**両方とも既存の `Cargo.lock` に在る**） |
| ③ 呼び出し側を async にしない | ✅ `SmtpTransport::relay(...).build()` → `Transport::send(&msg)` が **`async fn` も `.await` も無しでコンパイル成功** |
| 依存の増分 | ✅ **新規は 8 crate だけ**（`lettre` / `email-encoding` / `email_address` / `hostname` / `httpdate` / `nom` / `quoted_printable` / `webpki-roots`）。残りは既存と共有 |

**⚠ それでも却下した理由 3 つ:**

1. ⚠⚠⚠ **§1 の allow-list が作れず、しかも 060c の担保構造が使えない。**
   `docs/security.md` は「**宛先を allow-list で固定できない唯一の egress**（060c）」について、
   担保は「**毎回の明示同意**」＋「取得できる形を極端に狭める専用ガード」の**2 本しかない**と書いている。
   ⚠ **自動送信は「毎回の明示同意」と定義上両立しない。**
2. ⚠⚠ **信頼の根が 2 系統になる。** lettre は `webpki-roots`（**crate に焼き込まれた root CA**）を引く。
   既存アプリは `rustls-platform-verifier` / `rustls-native-certs`（**OS の信頼ストア**）を使っている。
   ⇒ 失効への追随が「OS の更新」と「crate のバージョン上げ」の 2 系統になる（§10 の新しい性質）。
3. ⚠ **配信者の私的なメールアドレスが視聴者に渡る。** SMTP の `From:` は配信者本人である。
   ⚠⚠ **要望に含まれていない、逆向きの個人データ露出**で、しかも取り消せない。

### (3-b) ⚠ 案 B（`.eml` を書き出して既定のメールクライアントで開く）: **成立したが「自動」ではない**

`lettre` の `builder` feature だけで実測（**新規 6 crate・TLS ゼロ・tokio ゼロ・egress ゼロ・資格情報ゼロ**）。
⇒ **正しい RFC5322 + MIME の `.eml` を生成でき、`multipart/mixed` ＋ `Content-Disposition: attachment`
＋ base64 の PNG が載ることを実物で確認した。**

**⚠ 却下理由:**

1. ⚠⚠ **「自動送信」にならない**（(1-c) の依頼者の判断で却下済み）。
2. ⚠⚠ **`.eml` を開いても「新規作成画面」にはならない。** `From:` / `To:` が入った**完成した 1 通**なので、
   各クライアントは**受信メッセージとして開く**。送るには「再送信 / 転送」を選ぶ必要がある。
   ⚠ **これはフォーマットの性質**であって、クライアント固有ではない（文言だけが違う）。
3. ⚠ **書き出したファイルにアドレスが残る**（§9）。⇒ 掃除の設計が要る。

### (3-c) ⚠ 案 W（Twitch のウィスパー＝DM）: **本人には届くが、画像を運べない**

公式ドキュメント（`dev.twitch.tv/docs/chat/whispers/`）の実測:

| 項目 | 内容 |
|---|---|
| エンドポイント | `POST /helix/whispers`（⚠ **`api.twitch.tv` は既に allow-list 済み**＝**新規 egress 先ゼロ**） |

⇒ **送れるのはリンクだけ**で、⚠⚠ **リンクは転送できる**（当選者が他人に渡せる）。
⚠ 転送を防ぐ唯一の方法はサーバーを要求する（(1-e) ③）。⇒ **却下。**

⚠ **なお、この案は他の点では非常に安かった**（記録として残す）:
**視聴者の入力ゼロ・新規依存ゼロ・新規 egress 先ゼロ・画像ファイルの取り込み不要・
メールアドレスを一切扱わない**。実装は既存の `TwitchChatSender`（066）の**兄弟として書ける**

### (3-d) ⚠ 案 C（公開チャットに景品リンクを載せる）: **最も安いが、全員が見られる**

  ⇒ **端末にメールアドレスを残さずに済んだ**（後始末が不要になった）。
