## 現在の前提（2026-08-22・公開情報で一次確認済み）

  「2026年3月8日現在　Windowsのみ」）／動画再生に **Windows Media Player が必要**／
  ⚠⚠ **Twitch メインアカウントの認証が必須**（あらかじめ登録した電話番号の SMS、未登録ならアカウント作成時のメール）。

    ①中身の準備 ②レアリティと確率を決める ③抽選箱を作成し**コピペ用の抽選タグ**を作成

    ⑥**抽選タグ毎にオペレーションへ重み付けをする** ⑦試し引きで確認。
  - ⚠ **経路 2（公式が宣伝するフォルダ経路）**——公式配布ページ:
    「**素材の入っているフォルダを指定するだけでガチャが作れます。サンプル同梱。**」

    解説記事 1 本のみが具体手順を書いている:「抽選箱一覧」⇒「追加」⇒「名前」⇒
    「フォルダーからガチャを生成」⇒ローカルフォルダ選択⇒「セット」。同名ファイル
    （`hitsuji.mp3` / `hitsuji.png`）は**同じ抽選タグにまとまる**。
    ⚠⚠ **確率は「確率ごとにフォルダを分け、フォルダ名に数字を入れる」**（「3」「97」等）
    ＝ **重みの設定もフォルダ名で終わる**。⚠⚠ **この一点は解説記事 1 本にしか根拠が無い（未確認）。**

  ⚠⚠ **UI は％も合計も出していないと読める**——Wiki が**手計算の手順を教えている**

  ⚠ 1 つの抽選タグに 2 つ以上のオペレーションを付けると**抽選タグの重みは合計値**になる。

  位置・音量・遅延／利用可能ユーザー／禁止ユーザー／コンボ値／オペレーション種別

### ⚠⚠ 「if 文をたくさん書く」の実体（2026-08-22 に確定）

**条件式もスクリプトも書かない。** Wiki・解説記事・公式のどこにも記述が無く、
確率変動（サブスク／VIP 限定）ですら「**初期設定では利用可能ユーザーが全員にチェックが
ついているので全員のチェックを外して確率が変動してほしい役割を選択します**」＝
**チェックボックス UI** である（Wiki「サブスクとVIPのみガチャ確率UPのやり方」）。

⚠⚠ **要望⑦の出所である N1 インタビュー（2026）の逐語に、既に答えが書かれていた**——
本人は「**イフみたいな Excel の IF 関数みたいな感じ**」と**比喩として**述べており、
実際に指しているのは次の反復である:

> 「…**どれぐらいの確率? 重みなんだか100の何ぐらいの確率で**、…**全部1個ずつなんか1段階ずつ
> どんどんどんみたいな「ガチャ当たり確率／ガチャ外れ確率／ガチャ外れ確率／ガチャ外れ確率」
> みたいにやんなきゃいけなくて**」（N1 インタビュー・2026）

⇒ ⚠⚠ **本スパイクの中心論点は「if 文の有無」ではなく、
「フォルダ経路がこの反復を消しているかどうか」（論点 A）である。**

## このタスクでやること（検証項目）

### (1) 「if 文をたくさん書く」の実体を特定する → ✅ **確定（2026-08-22）**

- **条件式もスクリプトも書かない。** 公開ドキュメント・Wiki・解説記事のどこにも記述が無く、
  確率変動ですら**チェックボックス UI**（上記「『if 文をたくさん書く』の実体」節が正）。
- ⚠⚠ **「if 文」は N1 インタビューの逐語では「Excel の IF 関数みたいな感じ」という比喩**であり、
  実体は**手順 4（タグのコピペ）＋ 重みの逐一入力**である。
- → **1 文の結論**: 「**たぬえさ3 でガチャを作るとき、配信者が一番手間だと感じるのは、
  画面に％が出ないまま、決めた当選確率を自分で『クジの本数』へ換算し、
  景品ごとに 1 件ずつ編集画面を開いて入力する反復である。**」

### (2) 確率・重みの指定方法 → ✅ **確定（2026-08-22）**

- **重み指定**（合計値に対する比率）。本数指定でも％指定でもない
  （Wiki「ガチャの重み付け」＝「当たりクジの本数」）。
- ⚠⚠ **「合計を 100% にする作業」は仕様上は不要だが、実際には手作業が発生している**——
  Wiki が「**確率をパーセンテージで決めた後、小数点がなくなるまで 10 倍や 100 倍にして計算**」と
  **％→重みの手換算を教えており**、総本数と確率の計算も手でやらせている
  （「総本数(1 + 2x5 + 10x2 + 50)=81本、大当たりの確率は1/81＝1.23…％」）。
- ⚠⚠ **その結果、N1 インタビューの本人は「重みなんだか 100 の何ぐらいの確率で」と
  重みと％の区別がついていない。** ＝ **「重みを入れたら％が横に自動で出る」は、
  この混乱を直接消す差別化点として生きている**（⚠ ただし手数全体に占める割合は小さい・(7) 参照）。
- 景品を 1 つ足したとき: **手動経路では他の景品の設定値を直す必要は無い**（重みは絶対値）。
  ⚠⚠ **ただし「意図した％」を保つには全部計算し直しになる。**
  ⚠⚠ **StreamDock のフラットな重み表もこの性質を解決しない**（行を足すと全員の％が動く）。
  ⚠ フォルダ経路なら「**フォルダ名で指定した確率が変わることはありません**」＝
  **段の確率が不変**（⚠ 解説記事 1 本のみが根拠）。

### (3) 景品 1 件あたりに設定する項目の数 → ✅ **確定（2026-08-22・Wiki「イベント設定」で裏取り）**

- **クールタイム／位置・音量・遅延／利用可能ユーザー／禁止ユーザー／コンボ値**、
  ＋ オペレーション種別（**メディア・HTML・URL・テキスト・Twitch チャット** 等）。
- ⚠ **表示時間に相当する独立した設定は見当たらない**（メディアの長さで決まると読める）。
  ⚠ StreamDock は 064b で「**表示時間は OBS に聞く**」（`GetMediaInputStatus`）と決めており、**同じ向き**である。
- ⇒ ⚠⚠ **StreamDock の表の列は「景品名／重み／確率（自動）／OBS ソース」の 4 つに絞る**。
  クールタイム・利用可能ユーザー・禁止ユーザーは**たぬえさ3 の複雑さの側**なので**足さない**
  （⚠ クールダウンは [061j](061j-keyword-conditions.md) が**条件ごと**に既に持っている＝景品ごとには要らない）。

### (4) トリガーの種類と、チャンネルポイント依存度 → ✅ **確定（2026-08-22）**

- **たぬえさ3 のガチャは、公開されている限りすべてチャンネルポイントで回されている。**
  Wiki「ソシャゲのガチャの作り方」は**チャンネルポイント関係カテゴリ配下**、解説記事 2 本ともチャネポ。
  ⚠ チャネポ以外でガチャを回している例は**見つからなかった**。
- ⚠⚠ **StreamDock はチャンネルポイントを扱えない**
  （`channel:read:redemptions` ＋ `channel.channel_points_custom_reward_redemption.add`
  ＝**新規 EventSub 購読＋新規スコープ＝既存ユーザーの再ログイン**・
  [043a](043a-monetary-ingestion-fidelity.md) の `bits:read` の先例）。
- ⚠⚠⚠ **帰結: 要望⑦を出した本人は、いまチャンネルポイントでガチャを回している。
  したがって、StreamDock のガチャをこのまま作っても、その人は使えない。**
- **選択肢（4 つ・推奨は (c)）**:
  - **(a) チャンネルポイント対応を別タスクとして起票** … ⚠ 既存ユーザー全員の再ログイン。
    ⚠ **本人の用途に応える唯一の道**。⚠ やるなら [063a](063a-gacha-definition-editor.md) より**先**
  - **(b) 課金トリガー限定**（ビッツ／サブスク／サブギフ／レイド） … ⚠ 本人の運用と違う。
    ⚠ 課金でしか回らないガチャは「視聴者が回す遊び」ではなくなる
  - **(d) チャット＋キーワード**（⚠ **当初の 3 択に無かった**） … ✅ **[061j](061j-keyword-conditions.md) で実装済み**
    （`contains` / `exact` ＋ 条件ごとのクールダウン・上限 60 秒）。**新規スコープゼロ**で、
    「視聴者が能動的に回す」性質はチャネポに最も近い。⚠ 「コストを払って回す」性質は再現できない
  - **(c) 063 系を保留（推奨・2026-08-22 に採用）**

### (5) OBS への出し方の差と、その影響 → ⚠⚠ **当初の想定が反転した（2026-08-22）**

- たぬえさ3 = ブラウザソース（`forOBS3` をローカルファイルとして読む）＝ **7 操作 1 回**。
  ⚠⚠ **これ 1 回で全エフェクトを永久にまかなえる**（景品を増やしても操作は増えない）。
- StreamDock = ⚠⚠ **064 の方針転換により「OBS 側のソースを鳴らす」方式**になった
  （`EffectObsSource = { kind:"obs-source"; sourceName }`）。
  ⇒ **景品 1 個につき、ユーザーが OBS 側にメディアソースを 1 本手で作る**必要がある。
- ⚠ [044a](044a-obs-auto-source-impl.md) の**ソース自動追加が対象にしているのはステージ窓
  （ウィンドウキャプチャ）だけ**で、景品ごとのメディアソースは自動追加されない。
- ⇒ ⚠⚠ **差別化点「OBS セットアップの手数は StreamDock のほうが少ない」は誤りになった。**
  景品 10 個で **たぬえさ3 は 7 操作、StreamDock は 7×10 ＋ α**。**差は景品数に比例して開く。**

### (6) 対応プラットフォームと対応 OS → ✅ **確定（2026-08-22）**

- ⚠⚠ **さらに たぬえさ3 は Windows 専用**（Wiki 動作環境「2026年3月8日現在　Windowsのみ」）。
  StreamDock は **macOS + Windows**。⚠ **依頼者自身が macOS である。**
- → **YouTube 配信者と macOS 配信者にとっては「たぬえさの代替」ではなく「唯一の選択肢」**になる。
  ⚠⚠ **2026-08-22 時点で、これが唯一そのまま生きている差別化点である**
  （(5) の OBS 手数は反転し、(1) の「簡単さ」は成立しなかった）。
