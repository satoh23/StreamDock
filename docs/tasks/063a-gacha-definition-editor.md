## 目的

ガチャを**作る体験そのもの**を実装する。

⚠⚠ **2026-08-22 改訂**: 要望⑦の文言は「たぬえさよりかなり簡単に作成できる」だが、
[063s](063s-tanuesa-gacha-spike.md) が **操作回数の総和では勝てない**ことを確定させた
（素材＝メディアソースの登録が OBS 側に残るため）。⇒ **本タスクの成否は「手順の少なさ」ではなく、
**画面の分かりやすさ**で測る:

1. ⚠⚠ **重みを入れると％が横に自動で出る**（たぬえさ3 は画面に％も合計も出さず、Wiki が手計算を教えている）
2. ⚠⚠ **1 画面・1 表で完結する**（たぬえさ3 は抽選箱 → 抽選タグ → オペレーションの 3 階層を行き来する）
3. ⚠ **「条件を追加」に相当する操作がゼロ**（行を足す＝景品を足す、だけ）

⇒ **N1 インタビューの痛点「重みなんだか 100 の何ぐらいの確率で」を直接消すのが 1 と 2 である。**

## このタスクでやったこと

### (1) ⚠⚠ データモデル＝**別テーブルを作らない**（穴 F の決定・SQLite ではなく localStorage）

**旧本文の `gachas` / `gacha_prizes` の 2 テーブル ＋ コマンド 9 本は採らなかった。**
採ったのは [063s](063s-tanuesa-gacha-spike.md) の「再開時にどこから始めるか」が推した**最小形**である:

```ts
// effectAssignments.ts
export type EffectAssignment = { kind: "none" } | EffectObsSource | EffectGacha;

export interface GachaPrize {
  name: string;        // ⚠ 空文字を許す（任意）。空なら OBS のソース名を表示に使う
  weight: number;      // ⚠ 1 以上 GACHA_WEIGHT_MAX 以下の整数（0 を許さない）
  sourceName: string;  // 鳴らす OBS のソース名（EffectObsSource と同じ規則で検証）
}
export interface EffectGacha { kind: "gacha"; prizes: readonly GachaPrize[]; }
```

- ⚠⚠ **確率は保存しない**（重みから毎回計算する）。保存すると重みと確率がずれ、
  「画面の％と実際の当たり方が違う」という**画面から理由が読めない**壊れ方になる。
- ⚠⚠ **Rust 差分ゼロ・新規コマンドゼロ**（＝§3 の攻撃面が 1 ミリも増えない）。
- **§8 の検証は frontend にある**が、これは既存の**キーワード条件とまったく同じ構え**である:
  1. **保存時と読み込み時の両方**で `parseConditions` → `parseAssignment` → `parseGachaPrize` を通す
     （規則が 1 つしかないので「片方だけ緩む」が構造的に起きない）
  2. ⚠⚠ **OS へ渡る値の壁は従来どおり sidecar 側の 2 枚**（`isAllowedObsSourceName` の形式検査 ＋
     **`GetInputList` との実在照合**）。⇒ **細工された localStorage 値が OBS 操作へ渡る経路は増えていない。**
  3. `docs/security.md` の保存ポリシーは**ユーザー自身の UI 設定値を明示的に除外**しており、
     ガチャ定義（景品名・重み・自分で付けた OBS のソース名）はそれに当たる。
- ⚠ **却下した案 (B)**: SQLite に 2 テーブル ＋ コマンド 9 本。§8 の検証を Rust 側に置ける利点はあるが、
  ⚠ **規模が数倍**で、**§3 の攻撃面（全窓から呼べるコマンド）が 9 本増える**。
  ⚠ 本タスクが守るべき値は「OBS のソース名」＝**既に localStorage 経路で扱っている値と同種**なので、
  保存先だけを分ける理由が無い。**再修正トリガー＝ガチャを複数保存して使い回したくなったとき**
  ⇒ ⚠⚠⚠ **2026-08-23 にこのトリガーを引いた**（依頼者の要望）。[063d](063d-gacha-library.md) が
  `{kind:"gacha"; prizes}` を **`{kind:"gacha"; gachaId}`** へ変え、ガチャ本体を別キーの一覧に移す。
  ⚠ **本タスクの `GachaPrize` / `parseGachaPrize` / `gachaDraw.ts` / `GachaPrizeTable` はそのまま流用される**
  （変わるのは「景品がどこにぶら下がっているか」だけ）。⚠ **063a-3 の芯を 1 つも壊さないこと。**
  （そのとき初めて「ガチャという実体」が要る）。

### (2') ⚠⚠⚠ **確率は「％」で直接入力する。行どうしを連動させない**

| 景品名 | 出る確率 | 当たったら | |
|---|---|---|---|
| 大当たり | `1` % | （OBS のソースを選ぶ） | ↑ ↓ 削除 |
| 当たり | `9` % | 〃 | ↑ ↓ 削除 |
| **合計** | **10.0%** | **何も出ない: 90.0%** | |

- ⚠⚠⚠ **これが 063s の痛点への直接の答えである**——痛点は「**％で決めたのに、それを自分で
  クジの本数（＝重み）へ手で換算させられる**」ことだった。⚠ **1 回目の実装（063a-1）は入力を重みのまま残し、
  ％を読み取り専用で横に出しただけ**で、**換算の作業を消していなかった**（順序が逆だった）。
- ⚠⚠⚠ **063a-2 の「いちばん下＝残り（自動）」は撤回した**（依頼者の指摘・2026-08-22:
  「**フォームに入力しても必ず 100% を超えないようにフォーム側が補正されるからめっちゃ使いにくい**」）。
  あの形は **行どうしを連動させ**、合計 100% を超える入力を**黙って直前の値へ戻して**いた。
  ⇒ **入力の順番に依存し**（先に下げないと上げられない）、**戻った理由も画面に出なかった**。
  ⚠⚠ **連動を作り直さないこと。**
- ⇒ **いまの規則（063a-3）**:
  - **1 行の％は、その行だけの値**。⚠ **他の行を見て制限しない・丸めない・戻さない。**
  - **合計が 100% 未満 → 残りは「何も出ない」**（＝はずれ。演出を出したいならはずれの行を足す）。
  - **合計が 100% 超 → 入力は戻さず、合計行の下に赤字で「○○% 多いです」と出し、直し方も書く。**
    ⚠ 止めるのは**テスト抽選だけ**。
  - 受け付けないのは「**その行だけで成立しない値**」のみ＝ 数値でない／0.1% 未満／100% 超。
- ⚠⚠⚠ **打った％がそのまま当たる確率になる**（`drawGachaPrizeIndex` の**分母は合計ではなく 1000 固定**）。
  ⚠ 合計で割ると「10% と打ったのに、他の行を足したら 9.7% になった」が起きる——
  **それがまさに「％が信用できない」であり、この画面が消すべきもの**である。
- ⚠⚠ **「％を勝手に直す」処理をコードから 1 つも持たない**（063a-2 の `normalizeGachaWeights` は削除した）。
- ⚠ **保存形は重みのまま**（`GachaPrize.weight` は 1〜1000 の整数＝ **重み 1 が 0.1%**）。
  ⚠⚠ **合計が 1000 である必要はない**（未満＝はずれ、超過＝直してもらう）。

### (2) 確率の丸め規則（穴 D の決定・⚠ **(2') の土台として生きている**）

⚠⚠⚠ **旧本文の完了条件「合計が常に 100.0% になる」は数学的に達成不能だった。**

| 重み | 各行の表示 | 丸めた％の和 |
|---|---|---|
| 1 / 3 / 6 | 10.0% / 30.0% / 60.0% | 100.0% |
| **1 / 3 / 3** | 14.3% / 42.9% / 42.9% | ⚠ **100.1%** |
| **1 / 1 / 1** | 33.3% ×3 | ⚠ **99.9%** |
| 1 ×7 | 14.3% ×7 | ⚠ **100.1%** |

⇒ **採った規則**: 各行は四捨五入して小数第 1 位まで出し、⚠ **丸めた％の和は画面に出さない**
（合計は必ず**重みの合計から直接** 1 回で出す＝ `gachaTotalPercentText`）。
⚠⚠⚠ **063a-2 の「合計行は固定表記 `100%`」は 063a-3 で撤回した**（改訂の記録 **N**）——
各行が独立して合計が 100% に固定されなくなった以上、`100%` と出すのは**嘘になる**。
⇒ **実際の合計を出し、足りないぶんは「何も出ない」、超過は赤字で伝える。**
⚠ 却下: **(b) 最大剰余法**＝個々の行が真値からずれ「1:1:1 なのに 33.4%」が説明できない／
**(c) 合計行を出さない**＝重みの合計（たぬえさ3 の「総本数」）が読めなくなる。
⚠ **規則は `gachaDraw.ts` の JSDoc とテストが正。** ⚠ **1/3/3 と 1/1/1 は必ずテストに入れること。**

### (3) 作成 UI（⚠⚠ **タブを増やさない**・穴 G の決定）

**既存の「エフェクトを表示する条件」の割り当てを「ガチャ」にすると、その行の下に表が開く。**

**表は (2') が正。** ⇒ **＋（景品を追加）とテスト抽選のボタンが 1 つずつ。**

- ⚠⚠ **3 枚目のタブにしなかった理由**: `ObsEffectsScreen` は「タブ 2 枚 ＋ **共通の下部**」で、
  下部（配信画面に表示／OBS へ自動で反映／前提ステータス）は**両タブの外**にある。
  タブを足すと、**ガチャが使わない出力窓の設定がガチャにも掛かって見える**。
- ⚠ **列は 4 つだけ**（[063s](063s-tanuesa-gacha-spike.md) の (7) が正）。
  たぬえさ3 の景品ごとの設定（クールタイム・利用可能ユーザー・禁止ユーザー・コンボ値）は**足さない**。
- ⚠ **景品名は任意**（穴 H の決定）。空なら OBS のソース名を表示に使う。
  ⚠ それでも列を残すのは、ソース名が `hazure_01.mp4` のような機械的な名前になりがちで、
  **「大当たり」と呼べないと確率表が読めない**ため。
- **OBS ソースの選択は既存部品を再利用**（`OBS_SOURCE_PREFIX` / `effectSelectAssignment` /
  `isObsSourceMissingFromList`）。⚠ **新しいセレクタを作っていない**（穴 B）。
- ⚠⚠ **列名は「OBS のソース」ではなく「当たったら」**——[063t](063t-gacha-output-types-spike.md) が
  **出力の型は 4 つあり StreamDock は 1 つしかできない**と確定させたので、
  **将来ここが増える場所**として名前を取り、**いまできることは注記で正直に断る**
  （「いまは当たったときに配信画面へ出すことだけができます」）。
- ⚠ **一覧が未取得・0 件のときは ＋ を押せない**（`sourceName` の無い景品は保存層が落とすため）。
  **押せない理由を画面に書く**（061a Q-1）。

### (4) テスト抽選（穴 E の決定＝**画面内にテキストのみ**）

- **1 回引いて結果を出し、あわせて「この画面を開いてからの累計内訳」を出す**
  （1 回では確率の体感が確かめられないため）。
- ⚠⚠ **OBS のソースは鳴らさない。** 却下した理由は 2 つ: ①**配信中に押すと本番の画面に出る**
  ②OBS 未接続だと何も起きず「壊れている」と読める。
- ⚠⚠ **§9: 結果は React の state にしか置かない**（localStorage にも DB にも書かない）。
  **窓を閉じれば消えるのが仕様**である。

### (5) ⚠ 空・不整合の扱い（穴 C の決定）

- **景品 0 件でも `{ kind:"gacha", prizes: [] }` のまま保持する**（`{kind:"none"}` へ潰さない）。
  潰すと「ガチャを選んだのに開き直すと『出さない』に戻っている」＝**黙って設定が消える**。
  UI は「景品がありません。」と出す。
- ⚠⚠ **OBS 側に無いソース名は警告する**（旧本文の「組み込み意匠へフォールバック」は
  **フォールバック先が存在しない**ので成立しない）。作法は 064b と**同じ文**を使う。
  ⚠ **一覧を 1 度も取っていないときは「無い」と断言しない**（064b と同じ規律）。
  ⚠ **一覧に無い名前でも `<option>` を自前で出す**——出さないとブラウザが先頭を選び、
  **黙って別のソースへ化ける**。

### (6) ⚠⚠ 発火層には触っていない（穴 I の決定）

- ⚠⚠⚠ **063a ではガチャは発火しない。** `createObsSourceMatcher` の `select` が `null` を返す＝
  **当たり判定の前に落ちる**ので、バースト枠もクールダウンも消費しない
  （061d-2 穴 γ 以来 4 回踏んだ罠を踏まないための形）。**抽選の本発火は [063b](063b-gacha-draw-and-triggers.md)。**
- ⚠ `effectTrigger.ts` は **1 文字も変更していない**（`git diff` で差分ゼロを確認済み）。
  `EffectRequestBase` の未使用 5 フィールドの返済も**していない**——
  返済の形が決まるのは「2 本目のレーンが何を要るか」が分かる 063b だから。
- ⚠ **黙って何も起きない状態を作らない**ため、表の上に
  「いまは作成とテスト抽選のみで、配信中の自動抽選はまだ動きません。」と**書いてある**。
  ⚠ **063b が入るまでこの 1 文を消さないこと。**

### (7) 抽選関数は本タスクで書いた（旧本文の宿題への回答）

旧本文は「最小限の抽選関数は本タスクで書いてよい（063b が本実装で置き換える）。
**どちらにするか実装時に決めてコメントに残す**」としていた。
⇒ ⚠⚠ **書いた。そして 063b はこれを置き換えず、そのまま使うこと。**
理由＝置き換えると「テスト抽選で見た確率」と「本番の確率」が別実装になり、
**本タスク唯一の差別化点（％が信用できること）が壊れる**。
