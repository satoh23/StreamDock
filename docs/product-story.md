# プロダクトストーリー

この文書は [README](../README.md) の「開発の背景」の詳細版です。ユーザーインタビューの手法・仮説の見直し過程・検証状況をまとめています。

## 開発の背景・課題発見

### 初期仮説：コメント管理の効率化

開発当初は、配信活動におけるコメント管理の負担に着目していました。

配信者はゲームプレイや視聴者とのコミュニケーションを行いながら、コメントを確認・管理する必要があります。

そこで当初は、コメントの閲覧や管理を効率化するツールを構想していました。

ただし、この段階での課題設定は、あくまで開発者自身の仮説でした。

**本当に配信者が困っていることなのか、既存ツールでは解決できていないのかを確かめる必要がある**と考え、実際の配信者へのインタビューを開始しました。

### N1インタビューの実施

Xなどを通じて配信者へ直接アプローチし、Google Meet等で個別インタビューを実施しました。

主に同時接続視聴者数30〜80人程度の配信者を対象とし、実際の配信活動における行動や課題を調査しました。

インタビューでは、単純に「このような機能が欲しいですか」と質問するのではなく、普段の配信準備や使用ツール、実際に発生している手間について聞くことを重視しました。

主な調査観点は以下のとおりです。

- 普段どのような配信を行っているか
- 配信開始前にどのような準備を行っているか
- OBS以外にどのようなツールを使用しているか
- それぞれのツールをどのように起動・設定しているか
- 配信準備で面倒に感じる作業は何か
- 面倒な作業に対して、現在どのような工夫や回避策を取っているか

インタビューの目的は、事前に考えた機能への賛同を得ることではなく、**配信者の実際の行動から課題を発見すること**でした。

> **インタビュー資料の取り扱い**
>
> インタビューは、文字起こしや個別の回答内容を外部公開しない約束のもとで実施しました。
>
> そのため、録音・文字起こし・参加者を特定できる情報は本リポジトリに掲載していません。
>
> 以下では、個人を特定できない範囲で課題を要約し、それらをもとに行った開発者自身の解釈と意思決定を記載しています。掲載内容は発言の逐語引用ではありません。

### インタビューで見えてきた課題

インタビューを通じて、コメント管理だけでなく、配信開始前の準備や複数ツールの運用にも負担があることに着目しました。

| 観察・ヒアリングで着目した課題                                              | 開発者としての解釈                                           |
| --------------------------------------------------------------------------- | ------------------------------------------------------------ |
| OBSやコメントビューア、読み上げソフトなど複数のツールを組み合わせて使用する | 配信環境の準備が複数の独立した操作に分かれている             |
| 配信のたびにツールの起動や設定確認が必要になる                              | 同じ作業を繰り返すこと自体が負担になる                       |
| 必要なツールを起動した状態にしておく運用もある                              | 起動し直す手間を回避したいというニーズが存在する可能性がある |
| コラボ配信時、DiscordのVCやURLを確認しOBSへ設定する作業が発生する           | ツール間で情報が連携されず、手作業が発生している             |

特に、コラボ配信においてDiscordの参加先を探し、必要なURLを取得してOBSに設定する作業が面倒だという具体的な事例がありました。

この課題は、単純なアプリ起動だけでは解決できません。

しかし、既存の配信ツールがそれぞれ独立しているため、利用者がツール間の操作を自分でつなぎ合わせているという、より広い課題を考えるきっかけになりました。

### 仮説の見直しとPivot

インタビューを経て、取り組む課題の範囲を見直しました。

|                    | 当初の構想               | 見直し後の構想                       |
| ------------------ | ------------------------ | ------------------------------------ |
| 着目した課題       | コメント管理の負担       | 配信準備・ツール操作の負担           |
| 解決アプローチ     | コメント支援機能の提供   | 既存ツールの操作を統合・自動化       |
| 主な利用場面       | 配信中                   | 配信開始前を中心に、配信中にも拡張   |
| 提供価値           | コメント管理を効率化する | 配信するための準備作業を減らす       |
| プロダクトの方向性 | コメント支援ツール       | 配信環境をまとめるデスクトップアプリ |

この方向転換は、コメント管理が不要だと判断したという意味ではありません。

コメント管理の改善だけを対象にするのではなく、配信者が既存ツールを利用する際の負担を、より広い観点で捉え直したものです。

結果として、コメントビューアはStreamDockの一機能として残しながら、プロダクト全体の中心を**配信準備の自動化**に置くことにしました。

## ユーザーインサイトとソリューション

### 個別の課題から共通構造を考える

インタビューで聞かれた困りごとは、一見すると異なるものです。

- 複数ツールを起動するのが面倒
- 毎回同じ準備を繰り返す必要がある
- ツール間の設定を手動で変更する必要がある

これらを個別に解決しようとすると、各ツールに対する専用機能を追加し続けることになります。

しかし、課題を整理する中で、個々のツールの機能不足だけではなく、**複数のツールを組み合わせて利用するための操作が、配信者自身に委ねられていること**にも問題があるのではないかと考えました。

### ユーザーインサイト

インタビューを通じて着目したのは、配信者が複数のツールを利用する理由と、それに伴って生まれる負担の関係です。

配信者は、単に多くのツールを使いたいわけではありません。

コメントの読み上げ、アバターの表示、視聴者参加型の演出などを取り入れることで、配信を盛り上げ、視聴者により良い体験を届けようとしています。

しかし、配信の質を高めるためにツールを追加するほど、起動・設定・管理など、配信の裏側で必要な作業も増えていきます。

つまり、**配信をより良くしようとする行動そのものが、配信者の運用負担を増やしてしまう**という矛盾があります。

ここから、次のインサイトを仮説として導きました。

> **配信者は、配信をより魅力的にするために多くのツールを活用したい。しかし、ツールを増やすほど管理の負担も増えるため、配信の質を追求することと、無理なく配信を続けることが両立しにくくなっている。**
>
> 配信者が潜在的に求めているのは、ツールの数や機能を減らすことではなく、表現の幅を広げながらも、それに比例して運用負担が増えない環境なのではないか。

### インサイトからソリューションへ

このインサイトを踏まえ、StreamDockでは「配信ツールを減らす」のではなく、「複数のツールを利用するための負担を減らす」という方向性を選択しました。

既存のOBSやコメントビューア、読み上げソフトなどを置き換えるのではなく、配信者が使い慣れた環境をそのまま活かせることを重視しています。

その第一歩として、ツールの起動・終了・起動順序の管理を自動化するプリセット機能を実装しました。

将来的には、単純なアプリ起動だけでなく、ツール間の設定や連携も含めた運用負担の軽減を目指しています。

### MVPの設計

最初のソリューションとして、配信開始前に繰り返し発生する操作を対象にしました。

| 課題                                     | 対応する機能             | 狙い                                   |
| ---------------------------------------- | ------------------------ | --------------------------------------- |
| 配信内容ごとに必要なツールが異なる       | プリセット管理           | 配信スタイルに応じて準備を再利用できる |
| 複数ツールを個別に起動する必要がある     | ワンクリック一括起動     | 起動操作の回数を減らす                 |
| ツールによって起動順序に制約がある       | 順次起動・並行起動の制御 | 手動による起動順序の管理を減らす       |
| 配信終了後に複数ツールを閉じる必要がある | 一括停止                 | 終了作業をまとめる                     |
| 起動できたか個別に確認する必要がある     | 起動状態の可視化         | 準備状況を確認しやすくする             |

開発対象を決める際は、すべての課題を一度に解決するのではなく、最初に価値を届ける範囲を配信準備の自動化に絞りました。

DiscordとOBS間の設定連携など、起動だけでは解決できない課題もありますが、まずは汎用的な起動管理をコア機能として構築し、そこから対応範囲を拡張する方針を取りました。

なお、ここでいうMVPは最初に検証する価値を絞った機能範囲を指します。v1.0.0には、追加のコメントビューア機能やOBS連携機能も含まれています。

## 開発・リリースと検証状況

### 開発からリリースまで

2026年7月5日に開発を開始し、2026年9月6日にv1.0.0をリリースしました。

企画、ユーザーインタビュー、仕様策定、技術選定、実装、テスト、セキュリティレビュー、リリースまで個人で取り組んでいます。

実装にはClaude Codeを活用しましたが、機能の優先順位やプロダクト方針、アーキテクチャの採否、セキュリティ要件などの意思決定は自身で行っています。

### ユーザー利用と現在の検証段階

リリース後は、実際にアプリを使用する配信者も獲得しました。

一方で、現時点ではユーザー数や定着率、配信準備時間の削減効果などについて、十分な定量的検証が完了しているわけではありません。

そのため、現段階で「複数ユーザーの課題を完全に解決した」「プロダクトマーケットフィットを達成した」とは考えていません。

現在の到達点は、**ユーザー調査から仮説を見直し、その仮説を検証するためのプロダクトを実際に開発・公開したこと**です。

### 今後検証したいこと

今後は以下の観点で、実際のユーザーに提供できている価値を検証したいと考えています。

| 検証項目       | 確認したいこと                                           |
| -------------- | ---------------------------------------------------------- |
| 準備時間の削減 | StreamDock導入前後で配信準備の所要時間が変化するか       |
| 操作回数の削減 | 配信開始前に必要な手動操作がどの程度減るか               |
| 継続利用       | 複数回の配信を通じて使い続けてもらえるか                 |
| 課題の再現性   | 異なる配信環境でも同様の課題が存在するか                 |
| 機能の優先順位 | 起動自動化とツール間連携のどちらに、より強い需要があるか |

機能を追加すること自体を目的とせず、実際にユーザーの行動がどう変わったかを判断基準として改善を進める方針です。
